# prod 배포 방법

**결론부터: `deploy/scripts/deploy.sh` 를 쓰세요. 수동 compose 명령을 직접 치지 마세요.**

```bash
ssh -p 2222 root@121.126.99.70
cd /opt/turnflow_backend
git pull origin main          # deploy.sh 도 내부에서 pull 하지만 미리 당겨두는 편이 안전하다*
bash deploy/scripts/deploy.sh
```

\* bash 는 스크립트를 바이트 오프셋으로 읽어간다 — 실행 도중 `git pull` 이 그 파일을 바꾸면
이후 라인을 잘못 읽을 수 있다. 미리 당겨두면 스크립트 안의 pull 이 no-op 이 된다.

롤백: `bash deploy/scripts/rollback.sh` (직전 이미지로. **마이그레이션은 되돌리지 않는다**)

## ⛔ 예전에 이 파일에 적혀 있던 절차 — 쓰면 안 됩니다

```bash
# 옛 내용 (2026-08-10 삭제)
docker compose -f docker-compose.prod.yml --env-file .env.production build
docker compose -f docker-compose.prod.yml --env-file .env.production up -d
docker compose ... up -d --force-recreate web celery_worker celery_beat
```

세 가지가 잘못됐습니다.

### 1. 인자 없는 `build` → **48초 DB 블립**

앱 이미지는 `web_webhook` 하나만 `build:` 컨텍스트를 갖고 나머지는 `image:` 로 공유합니다.
인자를 안 주면 buildx bake 가 **db 서비스 이미지**(`turnflow_instagram_db_pgbackrest:16`)까지 함께
구워 manifest 가 새로 생기고, 그러면 다음 `up -d` 가 **정상 동작 중인 db 컨테이너를 재생성**합니다.
2026-06-30·07-07·07-14·07-15·07-16 배포에서 매번 재현됐고 07-30 에 `build web_webhook` 으로 한정해
제거했습니다. deploy.sh 는 그 교훈이 반영돼 있습니다.

### 2. 인자 없는 `up -d` → db·redis·pgbouncer 까지 재생성

상태를 가진 티어는 **떠 있으면 손대지 않아야** 합니다. deploy.sh 는 running 이면 건너뜁니다.

### 3. `celery_beat` 기동 → **주기잡 이중 발사 (DM 중복 발송 위험)**

이 서버에는 **celery beat 가 없습니다.** 주기 실행은 전부
`CF cron 워커(turnflow-scheduler-tick, 매분) → POST /api/v1/internal/scheduler/tick` 으로 이관했고,
`celery_beat` 는 compose 에 `profiles: ["fallback"]` 로 빼놨습니다.
**그런데 서비스명을 명시하면 compose 가 프로필을 무시하고 기동합니다** — 그러면 beat 와 CF tick 이
동시에 돌아 같은 주기잡이 두 번 발사되고, DM 발송 계열 태스크가 중복될 수 있습니다.

또 `web` / `celery_worker` 는 **더 이상 존재하지 않는 서비스명**입니다.
현재 앱 서비스: `web_webhook` `web_dashboard` `web_external` /
`celery_dm` `celery_followup` `celery_default` `celery_billing` `celery_ai` `celery_reports`

## deploy.sh 가 대신 해주는 것

| 단계 | 내용 |
|---|---|
| 1 | 현재 실행 이미지를 `.deploy.prev` 에 기록(롤백 대상) |
| 2 | `git pull` **후** HEAD 로 태그 계산 → `build web_webhook` 만 |
| 3 | db·pgbouncer·redis 는 **running 이면 건너뜀** |
| 4 | 마이그레이션(PgBouncer 우회, db 직결) + collectstatic |
| 5 | web 3티어를 **하나씩** 교체(Caddy 가 살아있는 티어로 계속 라우팅) |
| 6 | celery 워커 5종 교체 + `celery_reports` 는 **진행 중 리포트 없을 때만**(1건 13~18분) |
| 끝 | **이미지 스큐 자동 점검** — 건너뛴 서비스를 놓치지 않게 |

## 배포 후 확인

```bash
# 스큐 없나 (deploy.sh 마지막 출력에 ✗ 가 없어야)
docker ps --format '{{.Names}}\t{{.Image}}' | grep turnflow

# 서비스
for p in 8001 8002 8003; do curl -s -o /dev/null -w "$p:%{http_code}\n" http://127.0.0.1:$p/api/v1/healthz; done

# 주기잡(tick)이 살아있나 — 이게 죽으면 결제 갱신까지 멈춘다
docker logs turnflow_instagram_web_dashboard --since 5m 2>&1 \
  | grep -cE 'POST /api/v1/internal/scheduler/tick HTTP/1.1" 200'
```
