## 1. 앱 정정 — 감사합니다, 문서를 고쳤습니다

운영 앱이 `11_turnflow_admin_app`(Capacitor WebView 셸)이라는 점 확인했습니다.
`capacitor.config.ts` 의 `server.url` 이 `admin.turnflow.link` 를 그대로 띄우는 구조까지
확인했고, 계약서 §5 를 다시 썼습니다.

- §5 의 SecureStore·`biometric.ts` 체크리스트는 **`12` 가 운영에 투입될 때로 미룹니다.**
- `device_id` 는 WebView localStorage 기준으로 문서화했습니다.
- **웹 배포 하나로 앱까지 커버된다**는 점을 롤아웃 절차에도 반영했습니다.

`12` 의 지문 로그인(생체로 잠근 SecureStore 에 refresh 보관)은 설계가 이미 이 계약과
맞물려 있어서, 투입 시점에 저장 토큰만 어드민 refresh 로 바꾸면 됩니다.

## 2. Q1 — 웹 완료 확인

MSW 목까지 만들어 흐름을 끝까지 밟아 보신 것 확인했습니다. §6 변경점 반영에 필요한 추가
작업은 크지 않을 것으로 봅니다(입력 필드 1개, 파라미터 1개, 화면 1곳).

## 3. Q2 — 마케팅 계정: 요청대로 구현했습니다

계약서에 빠져 있던 부분이 맞습니다. **`mfa_required: false` + `tokens` 를 그대로 내려줍니다.**

```jsonc
// POST /admin/auth/login/  — 마케팅 전용 계정
{
  "mfa_required": false,
  "tokens": { "access": "eyJ...", "refresh": "eyJ..." },
  "admin": { "admin_role": "marketing_viewer", "allowed_sections": ["marketing"] }
}
```

지금 짜 두신 분기(`tokens` 가 있으면 즉시 로그인, `mfa_required` 면 OTP 화면)가 그대로
동작합니다. 4xx 로 돌려보내지 않습니다 — 로그인 실패 한 번이 요청 두 번이 되는 것을
피해야 한다는 지적에 동의합니다.

**주의 두 가지:**
- 이 계정이 받는 것은 **일반 토큰**입니다(어드민 토큰 아님). 어드민 토큰 게이트가 제한
  역할을 제외하도록 만들어져 있어 정상 동작합니다. 갱신도 기존
  `POST /api/v1/auth/token/refresh/` 를 씁니다 — `/admin/auth/refresh/` 는 400 `not_admin_token`.
  → **갱신 URL 을 역할에 따라 갈라야 합니다.** `admin_role === "marketing_viewer"` 면 기존 URL.
- 마케팅 계정은 `GET /admin/auth/mfa/status/` 에서 `enrolled: false` 로 나옵니다. 보안 화면을
  아예 숨기시는 편이 낫습니다(등록해도 쓰이지 않습니다).

## 4. Q3 — refresh 수명: 신뢰 기기 7일로 올렸습니다

근거에 동의합니다. 신뢰 등록 자체가 이미 이메일 코드 1회를 통과한 기기이고, 해제 수단이
화면에 있습니다. **약해지는 것은 refresh 수명뿐이고 access 는 2시간 그대로**라, 권한 회수
(스태프 해제·기기 해제)가 반영되는 지연은 늘지 않습니다.

| 기기 | access | refresh |
|---|---|---|
| 신뢰 기기 (`device_trusted: true`) | 2시간 | **7일** |
| 비신뢰 기기 | 2시간 | 12시간 |

`remember_device: true` 로 2단계를 통과하면 신뢰 기기가 됩니다. 폰 WebView 에서 12시간마다
인증앱을 옮겨 적는 흐름은 이제 없습니다.

수명은 서버 설정(`ADMIN_REFRESH_TRUSTED_DAYS`)이라 배포 없이 조정 가능합니다 — 써 보시고
길거나 짧으면 알려주세요.

## 5. Q4 — 필드 4종 + 재발급 API 전부 추가

**백업코드 재발급 엔드포인트가 계약서에 없던 것, 저희 누락이 맞습니다.** §4 체크리스트에만
적고 §3 에 API 를 안 썼습니다. 404 날 버튼을 두지 않으신 판단이 맞습니다.

```
POST /api/v1/admin/auth/mfa/backup-codes/regenerate/
  ← { "password": "...", "code": "123456" }      // 비밀번호 + 현재 인증앱 코드
  → { "backup_codes": [ ...10개 ], "remaining": 10 }
```

비밀번호와 현재 코드를 함께 받는 이유는, 탈취된 access 토큰만으로 **복구 수단을 새로
뽑아가지 못하게** 하기 위해서입니다. 재발급하면 **기존 코드는 전부 폐기**됩니다 —
"종이에 적어둔 옛 코드는 버리세요" 안내를 넣어주세요.

`GET /admin/auth/mfa/status/` 에 요청하신 필드를 넣었습니다.

```jsonc
{
  "enrolled": true,
  "confirmed_at": "2026-08-20T04:12:00Z",
  "backup_codes_remaining": 8,
  "backup_codes_low_threshold": 3,        // ← 서버가 정한 기준. 프론트 하드코딩 대신 이 값과 비교
  "last_login_at": "2026-08-21T09:02:11Z",// ← 계정 단위
  "trusted_devices": [{
    "id": 1, "device_id": "3f2b...", "label": "이재원 MacBook",
    "is_trusted": true, "is_current": true,
    "created_at": "2026-08-18T02:11:00Z", // ← 추가
    "last_seen_at": "2026-08-21T09:02:11Z",
    "last_seen_ip": "121.130.44.14",
    "expires_at": null                    // ← 항상 null (아래)
  }]
}
```

- **`backup_codes_low_threshold`**: 3개로 정했습니다. 프론트가 3을 하드코딩하는 대신 이 값과
  비교해 주세요 — 기준이 바뀌어도 프론트 배포가 필요 없습니다.
- **`expires_at` 은 항상 `null` 입니다 — 신뢰에 만료를 두지 않기로 했습니다.** 실질 상한이
  이미 refresh 수명(7일)이고, 그 뒤에는 비밀번호와 인증앱을 다시 통과해야 합니다. 별도
  만료를 얹으면 보안은 거의 안 오르고 "왜 또 메일 코드가 오지"만 늘어납니다. 화면은
  **"해제할 때까지"** 로 반영해 주세요.
- **`is_trusted: false` 인 행도 옵니다.** 신뢰 등록 없이 들어온 임시 세션입니다(공용 PC 등).
  해제 대상에서 빼지 마세요 — 그것도 끊을 수 있어야 합니다.
- `is_current: true` 인 기기를 해제하면 본인이 로그아웃됩니다. 확인 모달 부탁드립니다.

## 6. Q5 — 기기 판정에 보조 신호는 넣지 않습니다

**지금 동작 그대로 두고 운영 안내로 처리하는 쪽**을 택했습니다. 미리 알려주셔서 감사합니다.

넣지 않는 이유는 두 가지입니다.

1. **막으려는 것을 못 막습니다.** `device_id` 위조가 우회하는 것은 "신규 기기 이메일 승인"
   한 단계뿐인데, User-Agent 는 헤더 한 줄 복사로 똑같이 위조됩니다. 방어력이 늘지 않습니다.
2. **오탐 비용이 큽니다.** 브라우저·WebView 가 업데이트될 때마다 UA 가 바뀌어 같은 기기가
   신규로 잡힙니다. 지금 걱정하신 "왜 또 메일 코드를 받지"를 **오히려 늘립니다.**

`device_id` 가 사라졌을 때 필요한 것은 이메일 코드 한 번이고, 그건 설계상 정상 동작입니다.
안내 문구에 쓰실 수 있게 정리하면 — *"앱 데이터를 지우거나 브라우저를 바꾸면 새 기기로
인식되어 메일 승인을 한 번 더 받습니다."*

## 7. 🔴 v1 에서 바뀐 것 3가지 (구현에 손이 갑니다)

죄송합니다. 실제로 짜면서 v1 계약이 안전하지 않거나 불충분한 지점이 나왔습니다.

### ① 백업코드는 `code` 가 아니라 **별도 필드** `backup_code` 입니다

v1 은 "`code` 에 인증앱 6자리 또는 백업코드 8자리"였는데, 6칸짜리 OTP 입력에 백업코드를
넣게 되는 구조라 UX 가 나빴습니다. 그리고 8자리(40비트)는 해시가 유출됐을 때 대입이
가능한 길이라 **12자리로 늘렸습니다.**

```jsonc
// POST /admin/auth/mfa/verify/
{ "challenge": "...", "code": "123456" }                    // 인증앱
{ "challenge": "...", "backup_code": "ABCD-EFGH-JKLM" }     // 백업코드 (별도 필드)
```

- 형식: `ABCD-EFGH-JKLM` (12자 + 하이픈 2개). **하이픈·공백·대소문자 무시**합니다 —
  사용자가 어떻게 쳐도 통과하니 프론트에서 정규화하지 마세요.
- 화면: OTP 화면에 "백업 코드로 로그인" 링크 → **일반 텍스트 입력 1칸**을 권합니다.
  지금 만드신 `OtpInput`(6칸)은 그대로 인증앱 전용으로 두시면 됩니다.
- 알파벳에서 `0/O`, `1/I` 를 뺐습니다(옮겨 적을 값이라).

### ② `mfa/confirm/` 은 **`setup` 이 준 `setup_token`** 을 항상 받습니다

v1 은 confirm 의 `setup_token` 이 "최초 등록일 때만" 이었는데, 등록 티켓이 필요한 건
재등록도 마찬가지라 **항상 필수**로 바꿨습니다. 흐름이 단순해집니다.

```
setup/   → 응답에 setup_token (새로 발급, TTL 300초)
confirm/ ← 그 setup_token 을 그대로 전달
```

### ③ 재등록(이미 등록된 계정)의 `setup/` 은 비밀번호 + **현재 코드**를 요구합니다

v1 은 `password` 만이었습니다. access 토큰이 탈취된 상태에서 비밀번호까지 알면 인증앱을
공격자 폰으로 옮길 수 있어, 현재 인증앱 코드를 한 번 더 받습니다.

```jsonc
// 재등록
POST /admin/auth/mfa/setup/   ← { "password": "...", "code": "123456" }
// 최초 등록 (변경 없음)
POST /admin/auth/mfa/setup/   ← { "setup_token": "..." }
```

### 그리고 빠진 것 하나 — `password_changed` 는 발생하지 않습니다

v1 §3-3 에 적었던 `password_changed` 사유 코드를 **뺐습니다.** 비밀번호 변경으로 토큰을
즉시 죽이는 기능을 넣지 않기로 했습니다(같은 구조를 전역으로 켜면 일반 회원까지 전부
재로그인하게 됩니다). 계정을 실제로 끊어야 할 때는 계정 비활성화·기기 해제를 씁니다.
분기를 넣어두셨다면 지워도 됩니다(해가 되진 않습니다).

## 8. 사유 코드 최종 목록

| HTTP | `details.code` | 언제 | 화면 |
|---|---|---|---|
| 401 | `invalid_credentials` | 비번 불일치·없는 계정·비스태프 (구분 없음) | 로그인 실패 문구 |
| 403 | `mfa_setup_required` | 인증앱 미등록. `setup_token` 동봉 | 등록 화면으로 |
| 400 | `invalid_code` | 인증앱/백업코드 오답 | 입력칸 유지, 재시도 |
| 400 | `invalid_email_code` | 메일 코드만 오답 | 해당 칸만 에러 |
| 400 | `challenge_expired` | TTL 초과 **또는 5회 실패로 파기** | 로그인 화면으로 |
| 400 | `already_enrolled` | 부트스트랩 경로를 등록된 계정이 사용 | 로그인 화면으로 |
| 400 | `setup_not_started` | QR 발급 없이 confirm 호출 | 등록 처음부터 |
| 400 | `not_enrolled` | 미등록 상태로 백업코드 재발급 | 등록 화면으로 |
| 400 | `not_admin_token` | 일반 refresh 를 `/admin/auth/refresh/` 에 | 로그아웃 |
| 401 | `token_expired` | refresh 만료·폐기 | 로그아웃 |
| 401 | `device_revoked` | 보안 화면에서 해제된 기기의 갱신 | 로그아웃 + 안내 |
| 401 | `user_inactive` | 계정 비활성/스태프 해제 | 로그아웃 |
| 403 | `admin_token_required` | **일반 토큰으로 `/api/v1/admin/**`** | 로그인 리다이렉트 |
| 404 | `device_not_found` | 남의 기기·이미 해제된 기기 해제 시도 | 목록 새로고침 |
| 429 | `RATE_LIMITED` | 로그인 5/분 · 코드 10/분 · 기기 메일 5/시간 | `retry_after` 표시 |

`challenge_expired` 가 **5회 실패에서도** 나온다는 점만 주의해 주세요. 지금 만드신 남은
시간 표시(`4:59`)에 더해, 이 코드를 받으면 시간이 남아 있어도 로그인 화면으로 되돌려야
합니다.

## 9. 롤아웃 — 요청 두 건 모두 반영

**"1번 완료를 알려 주시면 프론트를 올리겠다"** — 지금이 그 시점입니다. 다만 **dev 배포까지
끝난 상태**이고 prod 배포는 아직입니다. 아래 순서로 갑니다.

| 순서 | 주체 | 상태 |
|---|---|---|
| 1 | 백엔드 | 엔드포인트 구현 완료 · **dev 반영됨** · prod 배포 예정 |
| 1-b | 백엔드 | **prod 배포 완료를 별도로 알려 드립니다** ← 이 신호를 받고 올려주세요 |
| 2 | 프론트 | 웹 배포 (= 안드로이드 셸까지 자동 반영) |
| 3 | 관리자 3명 | 인증앱 등록 + 백업코드 보관 |
| 4 | — | **하루 확인 기간** (요청 반영) |
| 5 | 백엔드 | `ADMIN_MFA_ENFORCED=True` (env 만 전환, 재배포 아님) |
| 6 | 백엔드 | 문제 시 즉시 False 로 롤백 |

`/admin/auth/refresh/` 가 없는 상태로 프론트가 먼저 나가면 2시간 뒤 전원 로그아웃된다는
지적, 정확합니다. **prod 배포 완료 신호를 기다려 주세요.**

4→5 사이 하루는 그대로 두겠습니다. `admin_token_required` 경로를 실서버에서 확인하실 시간이
필요하다는 데 동의합니다. 확인 방법은 — 플래그를 켜기 전에 **일반 토큰으로 아무 어드민 API 를
호출**하면 됩니다(플래그가 꺼져 있으면 200 이라 재현이 안 되니, 켠 직후 30분 안에 확인해
주시면 롤백 여부를 판단하겠습니다).

## 10. 프론트가 알아서 한 것 — 전부 동의합니다

특히 두 가지가 서버 설계와 정확히 맞물립니다.

- **`device_id` 를 로그아웃해도 지우지 않는 것** — 맞습니다. 지우면 매 로그인이 신규 기기가
  되어 이메일 코드가 매번 갑니다. 서버도 로그아웃으로 기기 신뢰를 끊지 않습니다.
- **백업코드 화면에서 그냥 나갈 수 없게 한 것** — 서버는 해시만 갖고 있어 정말로 다시 줄 수
  없습니다. 재발급(§5)이 유일한 복구 경로입니다.

`qr_svg` 를 그대로 렌더하시는 것도 맞습니다 — `<svg>` 문자열로 내려갑니다.
