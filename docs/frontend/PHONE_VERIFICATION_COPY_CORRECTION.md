## 0. 왜 이 문서가 왔나 — 제가 수집 목적을 잘못 적었습니다

앞서 드린 전달문 3종이 전부 *"체험 종료 · 결제 실패 · 인스타 연결 끊김 같은 **중요 알림**을
보내려고 번호를 모은다"* 는 전제로 쓰여 있었습니다. **그 계획이 없습니다.**

실제 구조는 이렇습니다(2026-10-13 확정):

| 매체 | 보내는 것 | 보내는 주체 |
|---|---|---|
| **문자(SMS)** | **본인확인 인증번호. 이것 하나뿐입니다** | 우리 서버 (NCP SENS) |
| **알림톡** | 혜택·이벤트 등 **마케팅** (아직 미구현) | **마케팅 대행사**가 채널톡으로 |
| 이메일 · 홈 알림 | 결제 결과, 체험 종료, 연동 상태 | 우리 서버 — **종전 그대로, 변경 없음** |

→ **결제·체험 종료·연동 끊김 알림을 문자나 알림톡으로 보낼 계획은 전혀 없습니다.**

그래서 화면에 **「중요한 알림을 보내 드려요」**, **「체험이 끝나기 전 문자로 알려 드려요」**,
**「삭제하면 알림을 못 받습니다」** 같은 문장을 두면 **지키지 않을 약속 = 거짓 고지**가 됩니다.
제 전달문이 원인입니다 — 죄송합니다.

> 💡 참고로 번호를 모으는 실제 이유는 **마케팅 도달 확보**입니다. 메일 오픈율이 알림톡의
> 1/5 수준이고, 인스타로 가입한 349명은 자리표시 이메일(`@ig.invalid`)이라 메일조차
> 못 받습니다. 어떤 메시지를 어느 매체로 보낼지는 **마케팅 대행사가 정합니다** —
> 프론트가 신경 쓸 부분은 아니고, 아래 **동의 체크박스 하나**만 정확하면 됩니다.

## 2. ⭐⭐ 법정 동의 문구 2개 — 통째로 교체

여기가 이번 정정의 핵심입니다. **수집 목적이 바뀌었으므로 고지 문구도 바뀝니다.**

### 2-1. [필수] 휴대폰 번호 수집·이용 동의

```
[필수] 휴대폰 번호 수집·이용 동의
· 수집 항목: 휴대폰 번호
· 이용 목적: 본인확인 (중복 가입·무료체험 중복 수령 방지), 고객 문의 시 본인 확인
· 보유 기간: 회원 탈퇴 시까지 (관계 법령에 따른 보존 제외)
· 동의를 거부할 수 있으나, 거부 시 회원가입이 제한됩니다.
```

바뀐 건 **이용 목적 한 줄**입니다(종전: *"본인확인, 서비스 중요 알림(체험 종료·결제·연동 상태) 발송"*).

> **왜 이렇게 쓰는가** — 「서비스 중요 알림」을 목적에서 빼면 **필수로 받을 근거가
> '본인확인' 하나만** 남습니다(개인정보보호법 §16③ 최소수집). 그 하나를 버티게 하는 사실이
> **카드 없는 프로 30일 체험이 1인 1회**(`trial_used_at`)라는 점입니다 — 이메일만으로는
> 중복 수령을 막을 수 없으니 번호가 필요하다는 논리가 성립합니다. 그래서 목적에 그 사유를
> 구체적으로 적었습니다. 변호사 검토 요청서에도 같은 문안으로 올려 뒀습니다.

마지막 줄은 **법정 고지**입니다(§22의2). 빠뜨리면 안 됩니다.

### 2-2. [선택] 광고성 정보 수신 동의

```
☐ (선택) 혜택·이벤트 등 광고성 정보 수신에 동의합니다. (문자 메시지)
   미동의 시에도 회원가입·서비스 이용에는 제한이 없습니다.
```

종전 둘째 줄(*"미동의 시에도 체험 종료·결제 안내 등 서비스 필수 알림은 발송됩니다"*)은
**보내지 않는 것을 보낸다고 적은 것**이라 삭제했습니다.

> 🔴 **이 체크박스가 이번 프로젝트의 본체입니다.**
> 번호를 모으는 목적이 마케팅인데, **광고성 발송은 이 동의가 있어야만 가능합니다**
> (정보통신망법 §50). 번호를 100% 모아도 체크율이 30%면 마케팅으로 닿을 수 있는 사람은
> 30% 입니다. **번호 수집률이 아니라 이 체크율이 실제 성과 지표입니다.**
>
> 그렇다고 기본 체크·선체크·다크패턴은 **안 됩니다**(사전 동의 원칙 위반, 과태료 대상).
> 혜택을 솔직하게 보여 주는 문구로 자발적 체크를 끌어내 주세요.
> 퍼널 이벤트에 **동의 체크 여부를 같이 실어 주시면** 체크율을 추적할 수 있습니다
> (예: `phone_verified` 의 속성에 `marketing_opt_in: true|false`).

**매체는 「문자 메시지」만 적습니다.** 알림톡은 아직 발송 수단이 없어서, 지금 적으면
받지도 않을 매체의 동의를 받는 꼴입니다. 나중에 대행사가 알림톡을 붙이면 **매체를 추가하는
재동의**가 필요합니다(§50은 매체별 동의).

### 2-3. 팝업·설정 화면의 거부 고지 (Q13 답변 — 변경 없음)

가입 화면은 **필수**라 「거부 시 회원가입이 제한됩니다」가 맞지만,
팝업·설정은 **선택 수집**이므로 반대 방향입니다:

```
동의를 거부하실 수 있으며, 거부하셔도 서비스 이용에 제한이 없습니다.
```

| **Q5** | 발송 실패 뒤 앞 코드가 살아 있는지 | **고치기 전에는 안 살아 있었습니다.** 순서가 `직전 무효화 → 새 행 → 발송` 이라 발송이 실패하면 **유효한 코드가 0개**였고, 이미 받아 둔 코드를 넣어도 `NO_PENDING_PHONE_VERIFICATION` 이었습니다. 순서를 `새 행 → 발송 → **성공 시** 직전 무효화`로 바꿨습니다. 이제 재발송 성공=직전 죽음 / 재발송 실패=**직전 생존** → **입력 칸을 막지 않는 게 맞습니다** |

| **Q7** | verify 에 `sms_marketing_opt_in` 을 **빼면** 지금 값이 유지되는지 | **유지됩니다.** 코드가 `if opt_in and not user.sms_marketing_opt_in:` 이라 **True 로 올리기만** 합니다 — 생략하든 `false` 를 보내든 **기존 값을 끄지 않습니다.** 번호 변경 창에서 숨기는 방식이 안전합니다. 끄는 건 `PATCH /auth/me/ {"sms_marketing_opt_in": false}` 하나뿐(설정 토글). 테스트로 못 박았습니다 |
| **Q9** | 국내 번호 없는 해외 사용자 | **`User.phone_required_exempt` 추가**(마이그 `authentication 0011`). 켜면 그 사람만 `required: false`. **프론트는 아무것도 안 하셔도 됩니다** — `required` 만 읽으면 풀립니다. 운영은 CS 확인 후 Django admin 체크. 영어 화면의 「고객지원 문의」 줄은 그대로 두세요. ⚠️ **가짜 번호를 채워 넣는 우회는 하지 마세요** — 남의 번호로 문자가 가고 지표도 오염됩니다 |

|---|---|---|
| **Q4** | 쿨다운·429 가 **보낸 번호에만** 걸리는지 | **번호 기준이 맞습니다**(`filter(phone=...)`). 오타 고친 번호는 즉시 발송 — **프론트 동작이 정확합니다.** 번호를 바꿔 가며 쿨다운을 피할 수는 있지만 의도된 설계고, 실질 방어는 번호별 5회/일 · IP 100회/일 · 전역 3,000건/일이 맡습니다 |
| **Q8** | 자동 30일 체험이 휴대폰과 무관하게 지급되는지 · `trial_granted` 30일이 카드 없이 시작되는지 | **완전히 독립입니다.** `auto_trial` 은 휴대폰 필드를 **전혀 보지 않습니다**(코드에 `phone` 0건). 조건은 체험 미사용 + 빌링키 없음 + free/active 뿐이고 **카드 없이 시작**, 만료 시 과금 없이 무료로 내려갑니다. `trial_granted`(보상 30일)도 같은 `auto_trial.grant()` 라 동일합니다. **알림만 인증 뒤로 미루고 지급 호출은 그대로** 두시는 방식, 맞습니다 |
| **Q12** | 혜택 1회 제한이 계정 기준인지 번호 기준인지 · 남의 번호를 넣으면 막는지 | **둘 다입니다.** 계정당 1회(`User.phone_reward_granted_at` → `reason: already_granted`) + **번호당 1회**(→ `reason: phone_already_rewarded`). 번호 기준이 있는 이유는 계정 10개로 같은 번호를 10번 쓰는 것을 막기 위해서입니다. **다른 계정에 이미 인증된 번호는 막지 않습니다 — 전용 에러 코드도 없습니다.** 인증은 정상 완료되고 **보상만 안 나갑니다**(한 사람이 대행사용/개인용 계정을 따로 쓰는 경우가 실재해서 일부러 열어 뒀습니다. 막으면 두 번째 계정을 영영 인증 못 합니다). → 문구는 「**번호당** 한 번만」이 정확하고 「계정당」은 절반만 맞습니다 |
| **Q13** | 팝업·설정의 거부 고지를 「거부 시 번호를 등록할 수 없습니다」로 바꾼 것 | **그 문장도 부정확합니다** — 동어반복이라 고지 기능을 못 합니다. 그 맥락은 **선택 수집**이므로 법정 문구는 **반대 방향**입니다: 「동의를 거부하실 수 있으며, **거부하셔도 서비스 이용에 제한이 없습니다.**」 §22① 의 취지가 "거부하면 무슨 불이익이 있는지"를 알리는 것이라, 불이익이 없으면 **없다고 적는 것**이 맞습니다. 가입 화면(필수)은 「거부 시 회원가입이 제한됩니다」 그대로 |
| **Q14** | 필수 고지 4줄을 같은 화면 「자세히」로 접은 것 | **조건부로 괜찮습니다.** 같은 화면에서 펼쳐지고 다른 페이지로 안 보내면 일반적으로 허용됩니다(「링크 뒤에 숨기지 말라」는 제 표현이 과했습니다 — 별도 페이지를 염두에 둔 말이었습니다). 둘만 지켜 주세요: ① **접힌 상태에서도 *수집 항목*·*목적*은 한 줄 노출**(보유 기간·거부 고지는 접어도 무방). ⚠️ 목적에 「알림」이라고 쓰지 마세요 — §0 대로 안 보냅니다 ② **카카오 심사 캡처는 펼친 상태로** 제출해야 합니다. 심사자는 캡처만 보므로 접힌 화면을 내면 "고지가 없다"로 판단됩니다 ← **이게 실질 위험입니다** |

### 4-3. 문구 관련 3건 — 이 문서 §1·§2 가 답입니다

| # | 질문 | 답 |
|---|---|---|
| **Q10** | 광고 동의 매체가 「문자·카카오 알림톡」인데 알림톡은 광고를 못 보낸다 | **지적이 정확합니다.** 매체는 **「문자 메시지」만** 적습니다 → §2-2. 알림톡은 아직 발송 수단이 없고, 나중에 대행사가 붙이면 **매체 추가 재동의**가 필요합니다(§50은 매체별 동의) |
| **Q11** | 체험 종료·결제 실패·연결 끊김 **알림톡이 실제로 나가는지** · 카톡 없는 번호는 문자로 대신 가는지 | 🔴 **질문의 전제가 제 잘못입니다.** 그 알림을 **문자로도 알림톡으로도 보내지 않습니다**(§0). 결제·체험 안내는 이메일·홈 알림이 종전대로 담당합니다. 알림톡 자체도 **미구현**이고(채널 0개), 나중에 붙는 건 혜택·이벤트 같은 **마케팅**이며 **대행사 소관**입니다. → 「카카오톡으로 알려 드립니다」·「중요 알림을 문자로」 **둘 다 지우세요**(§1) |
| **Q13·Q14 법무** | 변호사 확인이 필요한지 | §2 의 동의 문구는 **법무 검토 전 제 판단**입니다. 검토 요청서(`docs/legal/휴대폰번호_수집_약관개정_반영문안.md` §4)에 올려 뒀고, 의견이 오면 **문구만** 한 번 더 조정됩니다 — **API 는 그때도 안 바뀝니다** |

### 4-4. 프론트 결정에 대한 의견 — 전부 동의

| 프론트 결정 | 백엔드 |
|---|---|
| 킬스위치 2개 뒤에 숨김 + **프론트 배포 → 플래그 ON → `PHONE_REQUIRED_SINCE`** | ✅ 제안하신 **3단계가 제 2단계보다 안전**합니다. 그대로 가시죠 |
| 오류 문구를 `code` 별 프론트 KO/EN | ✅ 맞습니다. 서버는 `Accept-Language` 를 보지 않습니다(LocaleMiddleware 없음). 다국어는 **머신 키**로 내리는 게 이 저장소 방식입니다. ⚠️ **모르는 `code` 폴백은 `detail` 로** 해 주세요 — 제가 코드를 추가했는데 프론트 사전에 없으면 "처리하지 못했습니다"만 뜹니다 |
| 설정 화면은 플래그 없이 출시 | ✅ 안전합니다. `phone_verified` 는 이미 운영에 나가 있습니다 |
| 모르는 `reward.kind` → `none` 취급 | ✅ 정확합니다 |
| `phone` 을 화면에서 마스킹 | ✅ 의도대로입니다. 본인 데이터라 서버는 전체를 주고 노출 정책은 화면이 정합니다 |
| 퍼널 이벤트 이름·속성 | ✅ 그대로 쓰세요. 서버는 **이벤트 이름 화이트리스트를 두지 않습니다**(정본은 프론트). 번호를 안 싣는 것도 맞습니다. 🟡 §2-2 대로 **`marketing_opt_in` 속성만 추가** 부탁드립니다 |

> 📌 **API 상세 계약은 사내 API MCP(= dev OpenAPI 스키마)가 정본입니다.** 이번에 확인하다
> **4xx 예시가 스키마에서 통째로 유실되던 문제**(저장소 전체 0건)를 발견해 휴대폰 엔드포인트는
> 고쳐 뒀습니다. 이제 Swagger/MCP 에서 `code` 별 예시가 보입니다:
> `POST /auth/me/phone/` 400·429·502·503(머신 키 8종 + `retry_after`) ·
> `DELETE` 409 `PHONE_REQUIRED` · `POST .../verify/` 400(머신 키 3종 + `attempts_left`).

## 6. 카카오 심사 관련 (프론트 작업과 병렬)

- `/signup/phone` 이라는 **경로**와 그 화면 **캡처**를 카카오 「카카오계정(전화번호)」
  동의항목 심사에 제출합니다. 경로를 바꾸셔야 하면 **미리 알려 주세요.**
- 심사 캡처는 **고지를 펼친 상태**로 제출합니다. 접힌 화면을 내면 "고지가 없다"로
  판단되므로, 펼친 상태 캡처가 가능해야 합니다.
- 카카오 ② 비즈니스 정보 심사는 **심사 중**이고, 이게 끝나야 ③ 동의항목 신청이 열립니다.
  프론트 배포와 **직렬이 아니니** 기다리지 마세요.
