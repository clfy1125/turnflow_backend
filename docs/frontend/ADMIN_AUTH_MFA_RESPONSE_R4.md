# 어드민 4차 회신 — 403 응답 필드 확인 + 메일은 이미 나가고 있었습니다

회신: 백엔드 → 어드민 콘솔팀 · 2026-08-16
대상: `10_turnflow_admin/docs/ADMIN_AUTH_MFA_REPLY.md` (4차)

---

## 1. ✅ 두 필드 **이미 들어 있습니다** — 안전망 없이 1번 경로로 끝납니다

`device_verification_required` 와 `email_masked` 둘 다 1단계 403 에 실려 있습니다.
실제 응답 원문입니다(dev 에서 임시 계정으로 실제 HTTP 호출, prod 배포본도 같은 코드 —
`views.py:217-218` 대조 완료).

```jsonc
// POST /api/v1/admin/auth/login/  → HTTP 403
{
  "success": false,
  "error": {
    "code": 403,
    "message": "2단계 인증(인증앱)을 먼저 등록해 주세요.",
    "details": {
      "code": "mfa_setup_required",
      "setup_token": "pWksv8e8rz…",          // 43자
      "expires_in": 300,
      "device_id": "b42a4213-2e31-46cd-…",
      "device_verification_required": true,   // ← 있습니다
      "email_masked": "mf***91@test.com"      // ← 있습니다
    }
  }
}
```

**읽는 경로가 `error.details.*` 라는 점만 주의하세요** — 403 이라 표준 에러 봉투 안에
들어갑니다. 1단계 200 응답에서는 최상위인데 여기서는 한 겹 안입니다.

그러니 1번 경로(처음부터 메일 코드 칸 표시)가 그대로 동작하고, 사용자가 한 번 거절당하는
일은 없습니다. **2번 안전망은 그래도 남겨두시길 권합니다** — 비용이 없고, 신뢰 기기 판정이
바뀌는 경계에서 한 번 더 막아줍니다.

## 2. 🟢 메일은 **이미 정상 발송되고 있었습니다** (3건 성공)

"prod 가 첫 실제 발송 경로"라고 말씀드린 부분, 확인했습니다. 이미 나갔습니다.

```
08-16 13:41  sent  admin_device_code  attempts=1
08-16 13:43  sent  admin_device_code  attempts=1
08-16 13:57  sent  admin_device_code  attempts=1
```

세 건 모두 `sent`(Cloudflare 발송 성공), 재시도 0회입니다. 즉 **막혔던 건 메일이 아니라
입력칸 하나**였고, 코드는 그 시각에 실제로 메일함에 도착해 있었습니다. 진단하신 원인과
정확히 일치합니다.

> ⚠️ 재시도 시 참고: `admin_device_code` 는 **시간당 5회** 스로틀입니다. 오늘 3건을
> 썼으니 같은 IP 에서 그 시간대에 2번 더 여유가 있습니다. 초과하면 429 `RATE_LIMITED` 이고
> 한 시간 뒤 풀립니다. 등록 재시도를 몰아서 하실 때만 걸릴 수 있습니다.

## 3. 목이 다 받아주던 것 — 그 수정이 핵심입니다

`목이 받아주고 있어서 이번에 못 잡았습니다` — 이 진단이 이번 건에서 가장 값어치 있는
부분이라고 봅니다. 목을 서버와 **같은 조건으로 거절하게** 고치신 것이 재발을 막습니다.

저희도 같은 규칙을 씁니다 — 새 검증을 넣으면 **고장난 버전에 먼저 돌려서** 실제로 실패하는지
확인하고 나서야 통과를 신뢰합니다. 이번 MFA 구현에서도 재사용 방지 가드와 어드민 토큰
게이트를 일부러 꺼서 테스트가 빨갛게 되는 것을 확인했습니다.

## 4. R3 반영분 — 확인했습니다

- `pending_total` 폴백을 **존재 여부(`undefined`)** 판정으로 바꾸신 것 확인. 한 사이클 더
  두고 지우시는 것도 합리적입니다(구 캐시 응답 대비).
- 플래그 ON 은 **업무 외 시간**으로 잡겠습니다.
