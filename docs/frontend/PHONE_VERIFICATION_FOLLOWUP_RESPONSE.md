# 휴대폰 본인확인 — 프론트 확인 요청 회신

> **작성** 2026-10-13 · 백엔드 `3169d25` → 이 회신분 배포 후 갱신
> **대상** `backend-phone-verification-followup.md` (14건)
> **요약**: 14건 중 **7건은 코드를 고쳐서** 답했고, 5건은 현재 동작을 확정했으며,

## 0. 먼저 — 바로잡아야 할 것 3가지

### ⚠️ ⓪ **수집 목적 자체를 제가 잘못 적었습니다** (Q11·Q10·Q14 전부의 뿌리)

제 전달문 전체가 *"체험 종료·결제 실패·연동 끊김 같은 **중요 알림**을 보내려고 번호를
모은다"* 는 전제로 쓰였습니다. **그런 계획은 없습니다.** 2026-10-13 사장님 확인:

| 매체 | 무엇을 보내나 | 누가 보내나 |
|---|---|---|
| **문자(SMS)** | **인증번호. 이것 하나뿐입니다** | 우리 서버(NCP SENS) |
| **알림톡** | 캠페인 복귀 유도 등 **마케팅** | **마케팅 대행사**(채널톡) |
| 이메일·홈 알림 | 결제·체험 종료·연동 상태 | 우리 서버 (종전과 동일, 변경 없음) |

**결제·체험 종료 알림을 문자나 알림톡으로 보낼 계획은 전혀 없습니다.**
번호를 모으는 진짜 이유는 **마케팅 도달**입니다 — 메일 오픈율이 알림톡의 1/5 이고,
인스타 가입자 349명은 자리표시 이메일이라 메일조차 못 받습니다.

→ **화면에서 지워야 할 문구**: 「중요한 알림을 보내 드려요」, 「체험 종료·결제 안내를
받으려면」, 「알림을 못 받습니다」 — 전부 **거짓 고지**가 됩니다. 제 잘못입니다, 죄송합니다.

→ **§2(수집 동의)의 이용 목적도 바뀝니다.** 아래 ②를 보세요.

### ⚠️ ①「카카오톡으로 알려 드립니다」도 아직 쓸 수 없습니다 (Q11)

**알림톡 발송은 한 줄도 구현돼 있지 않습니다.** 확인한 사실:

- 코드베이스에 알림톡 발송 경로 **없음** (문서 주석에만 등장)
- `BIZ_MESSAGE`/`KKOBIZ` 설정값 **없음**
- NCP 콘솔에 Biz Message 서비스 ID는 있으나 **카카오톡 채널 0개**, 템플릿 등록 전

→ 알림톡은 **나중에 마케팅 대행사가 채널톡으로** 붙입니다. 지금 화면에 「카카오톡으로」를
쓰면 당장은 지킬 수 없는 약속입니다. 제안 문구: 「**혜택·이벤트 안내를 받을 번호를 등록해
주세요**」 — 실제 용도와 맞고, 알림톡이 붙어도 그대로 유효합니다.

### ⚠️ ② 동의 문구 2개가 바뀝니다 (Q10 지적이 정확합니다 + ⓪의 여파)

**(가) 필수 — 수집·이용 동의.** 「서비스 중요 알림」을 목적에서 빼면 **필수로 받을 근거가
본인확인 하나만** 남습니다. 그래서 그 하나를 구체적으로 적어야 버팁니다
(우리는 **카드 없이 프로 30일**을 1인 1회로 주므로, 중복 수령 방지가 실재하는 근거입니다):

> **[필수] 휴대폰 번호 수집·이용 동의**
> · 수집 항목: 휴대폰 번호
> · 이용 목적: 본인확인 (중복 가입·무료체험 중복 수령 방지), 고객 문의 시 본인 확인
> · 보유 기간: 회원 탈퇴 시까지
> · 동의를 거부할 수 있으나, **거부 시 회원가입이 제한됩니다.**

**(나) 선택 — 광고성 수신 동의.** 지적하신 대로 매체 문구가 틀렸습니다. 지금 확정된 발송
매체는 문자뿐이므로 문자만 적습니다(알림톡 발송은 추후 마케팅 대행사가 붙입니다):

> ☐ **(선택)** 혜택·이벤트 등 광고성 정보 수신에 동의합니다. **(문자 메시지)**
> 미동의 시에도 회원가입·서비스 이용에는 제한이 없습니다.

> 🔴 **이 체크박스가 이 프로젝트의 본체입니다.** 복귀 유도 알림톡은 **광고성**이라
> **체크한 사람에게만** 보낼 수 있습니다. 번호를 100% 모아도 체크율이 30%면 마케팅
> 모수는 30% 입니다. 그렇다고 기본 체크·선체크로 두면 **사전 동의 원칙 위반**이니,
> 혜택을 보여 주는 문구로 자발적 체크를 끌어내 주세요(다크패턴 말고).

카카오 채널을 붙여 브랜드메시지를 쓰게 되면 그때 **매체를 추가하는 재동의**가 필요합니다
(§50은 매체별 동의). 지금 "카카오 알림톡"을 써 두면 **받지도 않을 동의를 받는** 셈이고,
나중에 매체가 바뀌면 그 동의는 쓸 수 없습니다.

## 1. 코드를 고친 것 (7건)

### Q3 · 새로고침/기기 전환 뒤 2단계 복원 → **`pending` 블록 추가** ✅

`GET /auth/me/phone/` 응답에 추가했습니다. sessionStorage를 버리셔도 됩니다.

```jsonc
{
  "pending": {                      // 진행 중인 인증이 없으면 null
    "phone_masked": "010-****-5678",
    "expires_in": 142,              // 초
    "attempts_left": 5
  },
  "resend_after": 0,                // pending 이 있으면 **그 번호 기준**
  "daily_remaining": 4
}
```

`pending !== null` 이면 코드 입력 단계를 그대로 복원하시면 됩니다. 다른 탭·기기에서도
동작합니다.

### Q6 · 삭제 가능 여부 → **`deletable` 추가** ✅

같은 응답에 `deletable: true|false`. 409를 받아 보고 알 필요가 없습니다.
`false`면 [삭제]를 비활성화하고 「번호를 바꾸려면 새 번호로 다시 인증」을 안내하세요.

### Q5 · 발송 실패 뒤 앞 코드 생존 → **프론트 가정이 틀렸었고, 그쪽에 맞춰 고쳤습니다** ✅

**고치기 전에는 살아 있지 않았습니다.** 순서가 `직전 코드 무효화 → 새 행 생성 → 발송`
이라, 발송이 실패하면 **살아있는 코드가 하나도 남지 않았습니다.** 사용자가 이미 받아 둔
코드를 입력해도 `NO_PENDING_PHONE_VERIFICATION`을 받습니다.

순서를 `새 행 생성 → 발송 → 성공 시 직전 코드 무효화`로 바꿨습니다. 이제:

| | 결과 |
|---|---|
| 재발송 **성공** | 직전 코드 죽음 (두 코드 동시 유효 방지) |
| 재발송 **실패**(502/503) | **직전 코드 그대로 살아 있음** → 입력 칸을 막지 않는 게 맞습니다 ✅ |

양방향 모두 테스트로 못 박았습니다.

### Q9 · 국내 번호 없는 사용자 → **면제 필드 추가** ✅

`User.phone_required_exempt` (마이그 `authentication 0011`). 켜면 그 사용자만
`required: false`가 됩니다.

**운영 방법**: CS가 확인 후 Django admin에서 체크. 프론트는 아무것도 안 하셔도 됩니다 —
`required`만 읽으면 그대로 풀립니다. 영어 화면의 「고객지원 문의」 줄은 그대로 두세요.

> ⚠️ **번호를 가짜로 채워 넣는 우회는 하지 마세요.** 알림톡이 엉뚱한 사람에게 가고
> 수집 지표도 오염됩니다. 면제는 "번호가 없다"를 그대로 기록하는 방법입니다.

### Q2 · `paid_extended`의 다음 결제일 → **`trial_ends_at`에 담습니다** ✅

같은 필드에 넣었습니다(필드를 둘로 나누면 화면이 `kind`마다 다른 키를 읽어야 합니다).
유료 구독에서 그 값은 **다음 결제일**입니다.

> ℹ️ 다만 `paid_extended`는 **현재 비활성**입니다(`PHONE_REWARD_PAID_EXTEND_DAYS=0`).
> 갱신일을 미루면 실매출이 이연돼서 금액 결정이 필요한 항목이라 기본 OFF입니다.
> 지금은 절대 안 나오니 화면을 만들어 두시되 테스트는 불가합니다.

### Q1 · `reward.trial_ends_at`은 **적용 후**입니다 ✅ (프론트 해석 정확)

`verify` 200의 값 = 연장이 **반영된** 종료 시각. 발송 응답(`202`)의 `reward`도 같은
판정 함수를 쓰므로 **적용 후 예고값**입니다.

> ✅ **2026-10-13 추가 — 전/후 날짜를 서버가 내려줍니다.** `reward.trial_last_day_before` ·
> `reward.trial_last_day_after` (KST 날짜 문자열 `"2026-11-08"`). 「11/8 → 11/15」를 그대로
> 찍으시면 됩니다. `trial_granted` 는 체험이 없던 사람이라 `before` 가 `null`,
> `paid_extended` 는 체험이 아니라 둘 다 `null` 입니다(그쪽은 `trial_ends_at` = 다음 결제일).
> 아래 주의는 **여전히 유효**하니 역산은 하지 마세요.
>
> 💡 **「마지막 날」 계산을 직접 하지 마세요.** `trial_ends_at`은 *결제/만료가 일어나는
> 시각 그 자체*라 날짜로 찍으면 하루 더 써도 되는 것처럼 보입니다. 서버에 이미
> `UserSubscription.trial_last_day`(KST 마지막 이용일)가 있고, 구독 조회 API가 내려줍니다.
> 프론트가 UTC 자정 근처에서 −1일 역산하면 **하루가 틀어지고 그 숫자가 곧 고지 문구**가
> 됩니다(예전에 같은 사고가 있어 서버로 올린 값입니다).
> 「11월 13일 → 11월 20일」을 그리실 거면 **전/후 둘 다 서버 값**으로 받으세요 — 필요하면
> `reward` 의 `trial_last_day_before`/`after` 를 쓰시면 됩니다(위 ✅).

### Q7 · `sms_marketing_opt_in`을 빼고 보내면 **유지됩니다** ✅

코드가 `if opt_in and not user.sms_marketing_opt_in:` 이라 **True로 올리기만** 합니다.
생략하거나 `false`를 보내도 기존 값을 끄지 않습니다. 번호 변경 창에서 숨기는 방식이 안전합니다.

> 끄려면 `PATCH /auth/me/ {"sms_marketing_opt_in": false}` — 설정의 토글만 이 경로를 씁니다.
> 테스트로 못 박았습니다.

## 2. 현재 동작 확정 (5건)

### Q4 · 쿨다운·429는 **보낸 번호에만** 걸립니다 ✅

`PhoneVerification` 조회가 `filter(phone=...)`이라 **번호 기준**입니다. 오타를 고친 번호는
즉시 발송됩니다 — 프론트 동작이 맞습니다. 테스트로 못 박았습니다.

> 번호를 바꿔 가며 쿨다운을 우회할 수는 있지만 의도된 설계입니다. 실질 방어는
> 번호별 5회/일 · IP 100회/일 · 전역 3,000건/일이 맡습니다.

### Q8 · 자동 30일 체험은 **휴대폰 인증과 완전히 독립**입니다 ✅

`auto_trial`은 휴대폰 필드를 **전혀 보지 않습니다**(코드에 `phone` 0건). 지급 조건은
체험 미사용 + 빌링키 없음 + free/active뿐입니다. **카드 없이 시작**되고, 만료되면 과금
없이 무료로 내려갑니다.

`trial_granted`(보상 30일)도 같은 `auto_trial.grant()`를 호출하므로 동일합니다.
알림만 인증 뒤로 미루고 지급 호출은 그대로 두시는 방식, 맞습니다.

### Q12 · 보상 1회 제한은 **계정 기준 + 번호 기준 둘 다**입니다

| 제한 | 필드 | 효과 |
|---|---|---|
| 계정당 1회 | `User.phone_reward_granted_at` | `reason: already_granted` |
| **번호당 1회** | 같은 번호로 이미 받은 사용자가 있는지 조회 | `reason: phone_already_rewarded` |

번호 기준이 있는 이유: 계정 10개를 만들어 같은 번호로 10번 받는 것을 막아야 합니다.

**다른 계정에 이미 인증된 번호는 막지 않습니다.** 전용 에러 코드도 없습니다.
인증은 정상 완료되고 **보상만 안 나갑니다**(`reason: phone_already_rewarded`).
한 사람이 대행사용/개인용 계정을 따로 쓰는 경우가 실재해서 일부러 막지 않았습니다
(막으면 두 번째 계정을 영영 인증 못 합니다).

→ 문구는 「혜택은 **번호당** 한 번만 드려요」가 정확합니다. 「계정당」은 절반만 맞습니다.

### Q13 · 팝업·설정의 거부 고지 — **바꾼 문장도 부정확합니다**

「거부 시 휴대폰 번호를 등록할 수 없습니다」는 동어반복이라 고지 기능을 못 합니다.

그 맥락에서는 수집이 **선택**이므로, 법정 문구는 **반대 방향**입니다:

> 「동의를 거부하실 수 있으며, **거부하셔도 서비스 이용에 제한이 없습니다.**」

개인정보보호법 §22①의 취지는 "거부했을 때 무슨 불이익이 있는지"를 알리는 것입니다.
선택 수집인데 불이익이 없으면 **없다고 적는 것**이 맞습니다.
가입 화면(필수)은 전달문 원문(「거부 시 회원가입이 제한됩니다」) 그대로 두세요.

### Q14 · 필수 고지 4줄을 「자세히」로 접은 것 — **조건부로 괜찮습니다**

같은 화면에서 펼쳐지고 다른 페이지로 보내지 않는다면 일반적으로 허용됩니다
(「링크 뒤에 숨기지 말라」는 제 표현이 과했습니다 — 별도 페이지를 염두에 둔 말이었습니다).

다만 둘을 지켜 주세요:

1. **접힌 상태에서도 핵심이 보여야 합니다.** 최소한 *수집 항목(휴대폰 번호)*과
   *목적(**본인확인**)* 은 접지 말고 한 줄로 노출하세요. 보유 기간·거부 고지는 접어도
   무방합니다. ⚠️ 「알림」이라고 쓰지 마세요 — §0-⓪ 대로 보내지 않습니다.
2. **카카오 심사 캡처는 펼친 상태로** 제출해야 합니다. 심사자는 캡처만 보므로 접힌
   화면을 내면 "고지가 없다"로 판단됩니다. ← 이게 실질 위험입니다.

> ⚠️ 두 항목 모두 **변호사 검토 전 제 판단**입니다. 법무 검토 요청 목록
> (`docs/legal/휴대폰번호_수집_약관개정_반영문안.md` §4)에 이 두 건을 추가했습니다.

## 3. 프론트 결정에 대한 의견

| 프론트 결정 | 백엔드 의견 |
|---|---|
| 킬스위치 2개 뒤에 숨김 | ✅ 좋습니다. 운영 순서도 제안대로 하시죠 — **프론트 배포 → 플래그 ON → `PHONE_REQUIRED_SINCE`**. 제 전달문은 플래그를 몰라서 2단계로 썼는데, 3단계가 더 안전합니다 |
| 오류 문구를 `code`별 프론트 KO/EN | ✅ 맞습니다. 서버는 `Accept-Language`를 보지 않습니다(LocaleMiddleware 없음). 다국어는 **머신 키로 내려주는 것**이 이 저장소의 방식입니다. 다만 **모르는 `code`가 왔을 때의 폴백은 `detail`로** 해 주세요 — 제가 코드를 추가했는데 프론트 사전에 없으면 "처리하지 못했습니다"만 뜹니다 |
| 설정 화면은 플래그 없이 출시 | ✅ 안전합니다. `phone_verified` 필드는 이미 운영에 나가 있습니다 |
| 모르는 `reward.kind` → `none` 취급 | ✅ 정확합니다 |
| `GET /auth/me/phone/`의 `phone`을 화면에서 마스킹 | ✅ 의도대로입니다. 본인 데이터라 서버는 전체를 주고, 노출 정책은 화면이 정합니다 |
| 퍼널 이벤트 이름·속성 | ✅ 그대로 쓰세요. 서버는 **이벤트 이름 화이트리스트를 두지 않습니다**(정본은 프론트). 번호를 안 싣는 것도 맞습니다 |

## 4. 전달 누락 사과 + 재전달

`PHONE_VERIFICATION_FRONTEND.md`를 못 받으셨다니 죄송합니다. 저장소
`docs/frontend/PHONE_VERIFICATION_FRONTEND.md`에 있고 이번에 함께 보냅니다.

다만 **API 상세는 사내 API MCP(= dev OpenAPI 스키마)로 보시는 게 더 정확합니다.**
이번에 확인하다 **4xx 예시가 스키마에서 통째로 유실되던 문제**를 발견해 고쳤습니다
(저장소 전체 4xx 예시 0건이었습니다). 이제 MCP/Swagger에서 이렇게 보입니다:

```
POST /auth/me/phone/         400·429·502·503 → 머신 키 8종 + retry_after
DELETE /auth/me/phone/       409 → PHONE_REQUIRED
POST /auth/me/phone/verify/  400 → 머신 키 3종 + attempts_left
```

`code`별 분기를 짜실 때 **이 목록이 정본**입니다.

0. 🔴 **「중요 알림/체험 종료/결제 안내를 보내 드려요」류 문구를 전부 삭제** (§0-⓪)
   ← **가장 중요**. 우리가 문자로 보내는 건 인증번호뿐이고, 결제·체험 알림은 이메일입니다.
   대체 문구: 「**혜택·이벤트 안내를 받을 번호를 등록해 주세요**」
1. 필수 동의의 **이용 목적**을 「본인확인(중복 가입·무료체험 중복 수령 방지)」으로 (§0-②가)
2. 광고 동의 문구의 매체를 **「문자 메시지」**로 + 「미동의 시에도 서비스 이용에 제한
   없음」으로 (Q10 · §0-②나). **이 체크율이 곧 마케팅 모수입니다**
3. 팝업·설정의 거부 고지를 **「거부하셔도 서비스 이용에 제한이 없습니다」**로 (Q13)
4. 접힌 고지에 **수집 항목·목적은 노출** (Q14)
5. 혜택 문구를 **「번호당 한 번」**으로 (Q12)
6. sessionStorage 복원을 **`pending` 블록**으로 교체 (Q3)
7. [삭제] 버튼 활성화를 **`deletable`**로 (Q6)
8. 모르는 `code` 폴백을 **`detail`**로

**백엔드는 Q1~Q9 반영 배포 완료**, Q10·Q13·Q14는 법무 검토 목록에 추가했습니다.
