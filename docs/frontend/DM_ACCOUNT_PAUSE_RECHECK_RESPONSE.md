## 0. 결론 먼저

**만듭니다. 요청하신 계약 그대로입니다. `api.ts` 는 손대실 게 없습니다.**

다만 서버 구현에서 한 가지를 조심해야 합니다. 요청서대로 "대기열에서 1건 시험 발송"을
소박하게 구현하면 **실패했을 때 정지가 24시간에서 48시간으로 늘어납니다.** 사용자가
상황을 나아지게 하려고 누른 버튼이 상황을 두 배로 악화시킵니다. 이건 프론트가 아니라
저희가 풀 문제이고, 어떻게 푸는지는 §2에 적었습니다. **알고 계시면 좋을 내용이라 남깁니다.**

그리고 **요청서의 전제 하나가 오늘 데이터로 뒤집혔습니다.** "인스타그램 실제 제한은 30일"은

직접 영향이 있어서 §5에 따로 적었습니다. **결론부터 말하면 [확인하고 재개] 버튼의 가치가
생각하신 것보다 훨씬 큽니다.**

## 1. 재개 API 계약 — 요청하신 그대로 갑니다

```
POST /api/v1/integrations/dm-verification/recheck-send/
{ "ig_connection_id": "<uuid>" }
```

`dm-verification` 라우터에 붙이므로 기존 `queue-state` 와 **같은 인증·권한**을 씁니다.
없는 연동이면 404, 남의 워크스페이스면 **403** 입니다. `queue-state` 와 동일하니
프론트 에러 처리도 그대로 재사용하시면 됩니다.

### 응답 세 갈래 — 요청하신 형태 그대로

**(a) 아직 막힘**

```json
{ "resumed": false, "reason": "still_blocked", "action_block_cooldown_seconds": 52380 }
```

`reason` 과 잔여 초는 덤으로 넣습니다. 안 쓰셔도 됩니다.

**(b) 통과**

```json
{ "resumed": true, "queue_state": { ... } }
```

**(c) 너무 빨리 재시도**

```json
{
  "success": false,
  "error": {
    "code": 429,
    "message": "방금 확인했습니다. 잠시 후 다시 시도해주세요.",
    "details": { "code": "recheck_cooldown", "retry_after": 573, "cooldown_until": "2026-09-09T…" }
  }
}
```

`MigrationCooldownError` 와 **같은 봉투**입니다. `details.retry_after`(초)와
`details.cooldown_until`(ISO) 둘 다 들어갑니다. 프론트 어댑터가 그대로 붙습니다.

**정지 상태가 아닌 계정이 호출하면 409** 입니다.

```json
{ "success": false, "error": { "code": 409, "message": "…", "details": { "code": "not_paused" } } }
```

### 연타 차단은 서버에서 합니다

지적하신 대로입니다. 프론트 `disabled` 로는 새로고침도 다른 탭도 못 막습니다.
**계정당 10분에 1회**로 걸겠습니다. 근거는 아래입니다.

- 확인 1회 = Meta 로 **진짜 DM 1건**을 쏘는 것입니다. 무료 조회가 아닙니다.
- 차단 중 재시도는 제한 기간을 늘립니다. 이건 저희 추측이 아니라 이 기능의 설계 근거입니다.
- 10분이면 하루 최대 144회입니다. 실제 제한 해제는 시간 단위라 이보다 촘촘할 이유가 없습니다.

숫자를 조정하고 싶으시면 말씀해 주세요. 서버 설정값입니다.

## 2. ★ 계약 한 곳을 바꿔야 합니다 — 실패 시 정지가 2배가 됩니다

요청서의 동작 설명은 이렇습니다.

> 그 계정 대기열에서 DM 1건을 시험 발송합니다. 통과하면 대기열을 재개하고,
> 막히면(368) 정지를 유지합니다.

**"정지를 유지"가 코드상 자동으로 되지 않습니다.** 지금 구조는 이렇습니다.

발송 직전 게이트가 "이 계정 쿨다운이 남았나"를 봅니다. 남아 있으면 Meta 로 아예 안 보냅니다.
그래서 시험 발송을 하려면 **그 게이트를 통과시켜야** 합니다. 방법이 두 가지인데 결과가
정반대입니다.

**틀린 방법 — 쿨다운을 먼저 해제하고 보낸다**

368 이 다시 오면 서킷이 새 차단으로 인식합니다. 반복 차단은 시간을 2배로 늘리는 설계라
**24시간이 48시간이 됩니다.** 한 번 더 누르면 96시간, 상한 7일입니다.
사용자가 "혹시 풀렸나" 하고 세 번 누르면 일주일 정지입니다.

**맞는 방법 — 쿨다운은 그대로 두고 그 1건만 게이트를 우회시킨다**

368 이 다시 와도 서킷이 "이미 차단 중"으로 보고 아무것도 하지 않습니다. **정지가 원래
길이 그대로 유지됩니다.** 요청서가 의도한 동작이 정확히 이것입니다.

이렇게 만들겠습니다. **프론트 계약은 안 바뀝니다.**

> 참고로 이 차이는 오늘 실제로 확인했습니다. 저희가 수동으로 풀 때 쓰는 커맨드는 해제와
> 동시에 에스컬레이션 레벨을 0으로 내립니다. 그 조치를 8월 26일에 해둔 덕분에 9월 2일
> 재발이 48시간이 아니라 24시간이었습니다.

## 3. 재개 응답에 queue_state 넣습니다

배너·게이지·칩이 따로 폴링해서 최대 30초 동안 토스트와 정지 배너가 같이 보이는 문제,
재현하신 그대로입니다. `(b)` 응답에 `queue_state` 를 넣겠습니다.

**`GET /dm-verification/queue-state/?ig_connection_id=…` 와 완전히 같은 객체**입니다.
같은 빌더 함수를 부르므로 필드가 어긋날 일이 없습니다. 계정 스코프라 `scope: "account"`,
`campaign_id: null` 로 옵니다.

재개 직후라 `blocking_reason` 은 `null`, `action_block_cooldown_seconds` 는 `0` 입니다.
이 두 개만 보고 배너를 내리셔도 됩니다.

## 4. 확인 요청 2건 — 둘 다 맞습니다

### 4-1. "한 건씩 나가고 첫 건이 막히면 즉시 다시 정지" — 맞습니다

발송은 계정 단위로 직렬화됩니다. 동시에 여러 건이 나가지 않습니다. 첫 건이 368 을 받으면
그 즉시 계정 쿨다운이 걸리고, 남은 대기 건은 전부 발송 직전 게이트에서 멈춥니다.

**단서 하나만 알아두세요.** 위 §2와 같은 이유로, 재정지의 길이가 상황에 따라 다릅니다.

| 언제 | 재정지 길이 |
|---|---|
| 쿨다운 남은 상태에서 시험 발송이 실패 | **변화 없음** (원래 남은 시간 그대로) |
| 쿨다운이 자연 만료돼 자동 재개된 뒤 실패 | **2배** (24h → 48h → 96h, 상한 7일) |

앞의 것이 이 API 가 만드는 상황이고, 뒤의 것은 아무도 버튼을 안 눌렀을 때 원래 일어나는
일입니다. 화면에서 구분해 보여줄 필요는 없다고 봅니다.

### 4-2. "제한이 풀렸습니다"가 아니라 "DM 전송을 다시 시작했습니다" — 정확합니다

시험 발송 1건 성공은 그 순간 그 요청이 통과했다는 것 이상을 뜻하지 않습니다.

**정정 하나 — 저희가 "다시 막힌 적이 있다"고 말씀드린 적이 있다면 그건 부정확합니다.**
세 번의 수동 해제에서 368 재발은 **0건**이었습니다. 해제 후 실패한 건들은 전부 다른
사유(발송 전 댓글 삭제, 대화 보관)였습니다. 즉 경험적으로는 오히려 잘 통과합니다.

그럼에도 "풀렸습니다"라고 쓰면 안 되는 이유는 경험이 아니라 **구조** 때문입니다.
Meta 는 계정 제한 상태를 알려주는 API 를 주지 않습니다. 저희가 아는 건 "방금 보낸 한 건이
통과했다"뿐이고, 그게 30일 제한의 해제를 뜻하지는 않습니다.

문구 그대로 가세요. 저희도 같은 이해입니다.

## 5. ★ 요청서의 전제 하나가 오늘 뒤집혔습니다

요청서 배경에 이렇게 쓰셨습니다.

> 인스타그램 실제 제한은 30일, 우리 자동 정지는 24시간입니다.

**8월 26일 사례에서는 맞았습니다.** 고객 스크린샷에 30일 제한이 찍혀 있었고, 이의제기하니
같은 날 철회됐습니다.

**오늘 사례는 달랐습니다.** 같은 계정이 어제 새벽에 또 걸렸고, 고객 요청으로 오늘 오후에
저희가 수동으로 풀었습니다. **9.5시간 만입니다.** 결과는 이렇습니다.

| | 값 |
|---|---|
| 밀려 있던 대기 건 | 362건 |
| 성공 | 345건 (95.3%) |
| 사람 기준 도착 | 333명 중 322명 |
| 368 재발 | **0건** |

실패 17건은 발송 전에 댓글이 지워졌거나 상대가 대화방을 지운 경우입니다.
저희나 Meta 쪽 문제가 아닙니다.

**9.5시간 시점에 Meta 는 이미 막고 있지 않았습니다.** 30일이 아니었습니다.
자동 재개를 기다렸으면 14.5시간을 더 놀았을 겁니다.

이게 [확인하고 재개] 버튼의 값입니다. **생각하신 것보다 훨씬 자주 통과할 겁니다.**
"기다리면 자동 재개" 문구를 지우신 건 옳지만, 성공 경로를 너무 희박하게 그리지는 마세요.
버튼을 눈에 띄게 두셔도 됩니다.

### 덤 — 재발 시점에 규칙이 있습니다

이 계정 세 번의 차단 시각입니다.

| 회차 | 시각 (KST) | 요일 |
|---|---|---|
| 1 | 08-26 03:08 | 수 |
| 2 | 09-02 03:42 | 수 |
| 3 | 09-09 05:14 | 수 |

**전부 수요일이고 간격이 정확히 7일입니다.** 그 사이 발송량을 65% 줄였는데도 같은 요일에
떨어졌습니다. Meta 가 주 1회 배치로 훑는 것으로 보입니다.

다음 예상은 **9월 16일 수요일 새벽**입니다. 확정은 아니지만, 만약 맞다면 "언제 또 걸릴지
모릅니다"보다 나은 안내를 드릴 수 있습니다. 그때 관측하고 공유드리겠습니다.

## 6. 3번 — 재발 횟수는 드리고, 제한 종료 시각은 못 드립니다

### 재발 횟수: 줍니다 (새 필드 필요)

지금 저장하는 건 에스컬레이션 레벨 하나인데, 이건 재발 횟수로 쓸 수 없습니다.
저희가 수동 해제할 때 이 값을 0으로 내리기 때문입니다. 오늘도 내렸습니다.
그래서 3회 걸린 이 계정의 현재 값은 0 입니다.

**누적 카운터를 새로 답니다.** 수동 해제로 초기화되지 않는 값입니다.
`queue-state` 와 재개 응답 양쪽에 넣겠습니다.

```json
"account_block_history": { "trip_count": 3, "last_tripped_at": "2026-09-08T20:14:37Z" }
```

2회차 이상일 때 문구를 다르게 쓰시겠다는 것, 좋은 판단입니다. 반복되는 계정은 이의제기가
더 급합니다.

### 인스타그램 제한 종료 시각: 불가능합니다

**없다고 알려드립니다.** 가능성을 다 확인했습니다.

- Graph API 에 계정 제한 상태나 종료 시각 필드가 없습니다.
- 368 에러 응답에도 기간 정보가 없습니다. 코드와 메시지뿐입니다.
- 고객이 보는 30일 안내는 인스타그램 앱 화면에만 있고 API 로 안 나옵니다.

**남은 방법은 고객에게 직접 입력받는 것뿐입니다.** 앱에서 본 날짜를 넣게 하고 그걸 화면에
쓰는 방식입니다. 필요하시면 만들 수 있지만, 지금 단계에서는 과해 보입니다.
지금 쓰시는 "제한이 풀리지 않으면 전송되지 않습니다" 문장이 최선이라고 봅니다.

## 7. 4번 — 차단 기록, 실제 결함이 맞습니다

들으신 게 맞습니다. 이번 조사에서 3건을 겨우 복원했습니다. 원인은 두 가지입니다.

**첫째, 368 은 에러 코드 필드에 안 남습니다.** 368 은 재시도 대상이라 대기열로 되돌리는데,
그 경로가 재시도 횟수와 다음 시도 시각만 저장하고 에러 코드는 비워둡니다. 그래서 에러
코드로 368 을 검색하면 **0건**이 나옵니다.

**둘째, 두 번째 이후의 368 은 아무 흔적도 안 남습니다.** 검증 로그에 기록하는 코드가
"새 차단일 때만" 안에 들어 있습니다. 이미 차단 중에 들어온 368 은 그냥 사라집니다.

지금 3건을 찾은 방법은 전체 발송 로그의 검증 로그를 문자열로 훑는 것이었습니다.
느리고, 로그 보존 기간이 지나면 영영 못 찾습니다.

**고치겠습니다.**

- 368 은 재시도 경로에서도 에러 코드를 남깁니다
- 차단 중 반복된 368 도 전부 기록합니다
- 차단 기록에 유발한 발송 로그 ID 와 캠페인 ID 를 직접 저장합니다

프론트 작업은 없습니다.

## 8. 일정

| 항목 | 상태 |
|---|---|
| 1. 재개 API + 연타 차단 + 409 | 바로 착수 |
| 2. queue_state 동봉 | 1과 함께 |
| 3. 재발 횟수 (마이그레이션 1건) | 1과 함께 |
| 4. 차단 기록 보강 | 1과 함께 |

한 덩어리로 만들어서 개발 서버에 먼저 올리겠습니다. **정지 상태를 개발 서버에서 재현하는
커맨드가 이미 있어서** 프론트가 실제로 눌러보실 수 있습니다.

```
manage.py dm_account_pause --account <핸들> --pause --hours 21 --queue 47
```

이 커맨드로 정지 상태와 대기 47건을 만들 수 있습니다. 운영에서는 정지 주입이 막혀 있고
조회와 해제만 됩니다. 개발 계정에 정지를 걸어드릴 테니 말씀만 주세요.

배포 준비되면 다시 연락드리겠습니다.

## 부록 — 문구에 참고하실 사실 몇 가지

**정지 중에도 큐는 계속 쌓입니다.** 정지는 발송 직전 게이트라 새 댓글은 계속 들어옵니다.
오늘 사례는 9.5시간 동안 362건이 쌓였습니다. 시간당 38건입니다.
**"지금 N건이 기다리고 있습니다"를 보여주시면 이의제기 동기가 훨씬 커집니다.**
이 값은 `queue-state` 의 대기 건수로 이미 나가고 있습니다.

**2번째 DM 은 24시간 안에 안 나가면 영구히 못 나갑니다.** 팔로우 게이트의 자료 발송이
여기 해당합니다. 저희 정지도 24시간이라 정지 순간 발송 중이던 건은 자동 재개를 기다리면
초 단위 차이로 죽습니다. 세 번 다 재현됐습니다. **이것도 빨리 확인해야 할 이유입니다.**
`queue-state` 의 `waiting_window_risk` 가 이 위험 건수를 이미 주고 있습니다.

**실패해도 메시지를 잃지는 않습니다.** 시험 발송이 막혀도 그 건은 대기열로 돌아갑니다.
사라지지 않습니다. 「아직 제한이 풀리지 않았습니다」 화면에서 손실을 걱정하실 필요 없습니다.
