## 0. 한 줄 요약

어드민 라운드(11~18차)에서 다듬은 오류 사전은 **운영자용으로는 완성**됐지만, 그 문구가
`frontend_action` 을 통해 **유저 콘솔에도 거의 그대로 흘러가고 있습니다.** 이 문서는
**§2 문구 원칙**을 먼저 정하고, 그 원칙에 따라 운영 사유 24종을 **사용자가 실제로 구분해야
하는 8묶음**으로 접어 문구를 재작성합니다(U8 이 지연·종결로 갈려 사유 키는 9개).

## 1. 왜 지금 손봐야 하나 (내부)

### 1-1. 지금 어휘가 세 벌입니다

| 계층 | 위치 | 예시 |
|---|---|---|
| ① 운영자 사전 | `apps/admin_api/dm_error_catalog.py` | "창이 닫힌 뒤 도착한 요청" · "우리가 제때 못 보냄" |
| ② 서버 유저 문구 | `apps/integrations/dm_frontend_actions.py` | "메시지 발송 불가 (파라미터 오류)" · "Private Reply는 댓글 작성 후 7일 이내에만 가능합니다" |
| ③ 프론트 i18n | `src/locales/ko/translation.json` | "전송 오류" · "전송 창 만료" |

②가 가장 오래됐고(v3.2, 어드민 라운드 전에 작성) **가장 기술적**입니다. ③은 ②를 신뢰하지 않고
따로 라벨을 만들어 쓰고 있습니다.

**①이 ②로 새면 안 되는 이유**가 여기 있습니다 — ①은 *운영자가 원인을 파고들기 위한* 사전이라
내부 처리 사정("우리가 제때 못 보냄", "발송 처리기가 멈췄는지 확인")이 그대로 적혀 있습니다.
그 층은 어드민에만 남깁니다.

### 1-2. 프론트가 이미 백엔드 문구를 덮어쓰고 있습니다

```tsx
// src/app/pages/dm-auto/components/DMResultModal.tsx:46
// 백엔드 frontend_action 이 IG "Private Reply 7일 창 만료 / 댓글 삭제" 오류에 대해
// 'Private Reply · ID · 파라미터 오류' 같은 기술 용어를 그대로 내려줘서,
// 일반 사용자용 문구로 제목·설명만 덮어쓴다(심각도/CTA/타임라인은 백엔드 그대로).
```

지금은 subcode 2개만 덮어쓰지만, 새 오류가 생길 때마다 프론트 하드코딩이 늘고 그때마다
프론트 배포가 필요해집니다.

### 1-3. 같은 값을 두 이름으로 부르고 있습니다

| | 서버 | 프론트 |
|---|---|---|
| `status_group=attention` | **확인 필요** | **전송 실패** |

CS 가 화면을 보며 로그를 검색할 때 단어가 안 맞습니다. (§3 에서 제3안 제시)

## 2. 문구 작성 원칙

### 2-1. 문구 구조 — 세 부분

모든 오류 문구를 이 순서로 씁니다.

> **현재 상태 → 발생 이유 → 가능한 다음 행동**

| 부분 | 답하는 질문 | 생략 가능? |
|---|---|---|
| **현재 상태** | 지금 어떤 상태인가 | 불가 (제목) |
| **발생 이유** | 왜 이렇게 되었나 | 불가 — **단, §2-3 필터를 통과한 것만** |
| **다음 행동** | 무엇을 하면 되나 | **가능** — 할 일이 없으면 **그 줄을 아예 쓰지 않는다** |

> **'따로 조치하실 일은 없어요'를 전부 뺐습니다**(2026-08-07). 조치가 없는 사유에 그 문장을
> 붙이면 화면만 길어지고 정보가 늘지 않습니다 — **다음 행동 줄이 없으면 그 자체로 "할 일 없음"**
> 입니다. 지금 이 줄이 있는 사유는 실제로 할 일이 있는 것뿐입니다
> (연결·플랜 변경·캠페인 켜기·계정 선택·다른 툴 정리·재확인·문의).
>
> **'영향 범위'는 별도 항목에서 뺐습니다**(2026-08-06). 항목이 넷이면 화면이 길어지고, 실제로
> 범위가 필요한 사유는 일부뿐이었습니다. **범위를 모르면 오해가 생기는 경우에만 이유 문장
> 안에 함께 적습니다** — 예: U5 "게시물마다 제한 여부가 다를 수 있어, 다른 게시물에서는
> 정상적으로 발송될 수 있어요."

### 2-2. 작성 기준

| # | 기준 | ✕ | ○ |
|---|---|---|---|
| 1 | **주체를 탓하지 않고 상태를 설명** | 인스타그램이 막았어요 | 발송이 제한되어 있어요 |
| 2 | **차분하고 정돈된 말투** | 못 보내요 / 나가요 | 발송되지 않았어요 / 발송돼요 |
| 3 | **강한 표현은 꼭 필요할 때만** | 안 돼요 · 막혔어요 · 실패했어요 | 제한되어 있어요 · 완료되지 않았어요 |
| 4 | **기능명을 구체적으로** | 정상으로 나가요 | 자동 DM 발송은 정상적으로 진행돼요 |
| 5 | **최소한의 이유를 함께** | (결과만 전달) | 인스타그램의 자동화 정책 또는 시스템 판단에 따라 |
| 6 | **확인 안 된 원인은 단정 금지** (→ §2-4) | 댓글이 7일이 지났습니다 | 댓글 작성 후 시간이 지났거나, 댓글·게시물이 삭제된 경우일 수 있어요 |
| 7 | **범위 오해가 생길 때만 범위를 이유에 넣기** | (계정 전체가 막힌 줄 알게 둠) | 다른 게시물에서는 정상적으로 발송될 수 있어요 |
| 8 | **내부 용어 금지** | Private Reply · 파라미터 · 토큰 · 웹훅 · subcode | 댓글 답장 · 계정 연결 · 실시간 수신 |
| 9 | **내부 처리 사정은 쓰지 않음** | 발송 대기열이 밀려서 · 35분 동안 확인했지만 · 운영팀이 수동으로 정리 | (해당 부분을 아예 쓰지 않음) |
| 10 | **일어나지 않는 사유는 쓰지 않음** | 연결 유효기간(60일)이 지나서 | (서버가 6시간마다 자동 갱신 — 활성 계정엔 발생하지 않음) |

### 2-3. 이유(cause) 필터 — 무엇을 쓰고 무엇을 빼는가

기준 5는 "이유를 쓰라"이지만, **아무 이유나 쓰라는 뜻이 아닙니다.** 다음을 통과한 것만 씁니다.

| 통과 조건 | 판단 기준 |
|---|---|
| ① **사용자 쪽에서 확인·이해 가능한가** | 비밀번호 변경, 상대방 계정 상태, 시간 경과 → **씀** |
| ② **외부 요인인가** | 인스타그램 정책·판단·서버 오류, 상대방 사정 → **씀** |
| ③ **내부 처리 사정인가** | 발송 대기열, 검증 대기 시간, 운영 조치, 배치 주기 → **쓰지 않음** |
| ④ **실제로 일어나는가** | 자동 갱신되는 토큰 만료 등 → **쓰지 않음** |

③에 걸리는 사유는 **이유 칸을 비우는 게 아니라, 사용자에게 의미 있는 다른 층위로 올려서**
씁니다. 예를 들어 발송 적체로 시간이 지난 건은 "대기열이 밀려서"가 아니라
**"발송 가능 시간이 지났어요"** — 이것도 사실이고, 사용자에게 필요한 정보는 이쪽입니다.

> ⚠️ 대신 **사용자에게 숙제를 주지 않아야** 합니다. 원인을 밝히지 않는다면 "설정을 확인해
> 보세요" 같은 문장도 함께 빼야 합니다 — 확인해도 나오지 않을 것을 찾게 만들면 문의로
> 돌아옵니다. 이 경우 **다음 행동 줄 자체를 쓰지 않습니다**(2026-08-07 변경 — 아래 참고).

### 2-4. 관측한 것과 추론한 것을 구분한다

기준 6 의 실전 적용입니다. **우리가 실제로 관측한 것만 단정하고, 나머지는 가능성으로 씁니다.**

| 우리가 아는 것(관측) | 우리가 모르는 것(추론) |
|---|---|
| Meta 가 반환한 코드·상태 | 그 DM 이 상대 화면에서 **실제로 어디에 있는지** |
| 발송 요청을 보냈고 응답을 받았다는 사실 | 수신자가 **봤는지 안 봤는지** |
| 시간이 지났다는 사실 | 상대가 **왜** 계정을 지웠는지 |

예를 들어 `2534025` 로 우리가 아는 것은 **"수신자와 대화 채널이 열려 있지 않다"** 뿐입니다.
그 DM 이 요청함에 있는지 스팸함에 있는지는 관측할 수 없습니다.

| ✕ 단정 | ○ 가능성 |
|---|---|
| '숨겨진 요청'함으로 전달되었어요 | '숨겨진 요청 · 스팸함'으로 이동했을 수 있어요 |
| 인스타그램이 '숨겨진 요청'으로 분류해요 | 인스타그램이 '숨겨진 요청'이나 스팸함으로 분류할 수 있어요 |
| ~에 해당돼요 | ~에 발생할 수 있어요 |

**확정해서 얻는 것은 없고 잃는 것만 있습니다.** "요청함에 없던데요" 문의 한 건이면 그 화면의
모든 문구가 의심받습니다. 반대로 가능성으로 적으면 어느 쪽이어도 문구가 맞습니다.

> ⚠️ 단, **가능성 표현이 정보를 지우는 핑계가 되면 안 됩니다.** §2-3 에서 빼려는 것은
> **내부 처리 사정**이지 **사용자에게 유효한 사실**이 아닙니다. "스팸함"처럼 수신자가 어디를
> 봐야 하는지 알려주는 단어는 불안해 보여도 남깁니다 — 지우면 복구 기능이 왜 필요한지
> 설명되지 않습니다.

#### 실제로 걸러낸 사례 2건 — 둘 다 "업계에서 다들 그렇게 말하는 것"이었습니다

| 뺀 문구 | 왜 뺐나 |
|---|---|
| "연결 유효기간(60일)이 지나서" | `ig-refresh-tokens-pending-expiry` 가 6시간마다 만료 14일 전 토큰을 갱신하고 Meta 가 60일을 새로 발급한다 → **활성 계정에는 일어나지 않는다** |
| "비밀번호를 변경하셨거나" | **Meta 의 Instagram Platform 문서는 토큰 무효화 사유를 아예 다루지 않는다**(만료 기간만 명시). 널리 인용되는 이 문구는 **Facebook Login 의 `subcode 460`** 설명이고 우리는 Instagram Login 이다. 실제 로그에도 subcode 460 은 **0건**, subcode 없는 code 190 뿐 |

**둘 다 "그럴듯해서" 들어갔습니다.** 문구를 쓸 때 원인을 적으려거든 **① 공식 문서에 있는가
② 우리 로그에서 관측되는가** 를 확인하세요. 둘 다 아니면 빼는 편이 낫습니다 —
없는 원인을 적으면 사용자가 없는 것을 찾으러 갑니다.

### 2-5. 적용 예시

**수정 전**
```
제목    이 게시물에는 자동 DM을 보낼 수 없어요
설명    인스타그램이 이 게시물에 한해 자동 메시지를 막았어요.
        같은 계정이라도 다른 게시물은 정상으로 나가요.
```

**수정 후**
```
제목    이 게시물에는 자동 DM 발송이 제한되어 있어요
이유    인스타그램의 자동화 정책 또는 시스템 판단에 따라 이 게시물의 자동 DM 발송이
        제한되었어요.
        게시물마다 제한 여부가 다를 수 있어, 다른 게시물에서는 정상적으로 발송될 수 있어요.
```

| 무엇이 달라졌나 | 근거 |
|---|---|
| "보낼 수 없어요 / 막았어요" → "제한되어 있어요" | 기준 1·3 |
| "정상으로 나가요" → "자동 DM 발송이 제한 / 정상적으로 발송될 수 있어요" | 기준 4 |
| 이유 추가("자동화 정책 또는 시스템 판단에 따라") | 기준 5·6 — 외부 요인이므로 §2-3 ② 통과 |
| "이 게시물에 한해" → "게시물마다 제한 여부가 다를 수 있어" | 기준 7 — 범위를 이유 안에 |

### 2-6. 톤 레퍼런스

`apps/integrations/connection_health.py` 의 `_ISSUES` 가 가장 가깝습니다 —
*"댓글·메시지 실시간 수신(웹훅)이 꺼져 있어요. 재구독하면 복구돼요."*
내부 용어("웹훅", "재구독")만 바꾸면 이 원칙에 맞습니다.

## 3. 상태 그룹 5종 (탭·배지)

**결론: 이번 라운드에서 그룹 라벨은 하나도 바꾸지 않습니다**(결정 ①②).

| 머신값 | 서버(`GROUP_DISPLAY`) | 프론트 i18n | 유저에게 보이는 것 |
|---|---|---|---|
| `waiting` | 대기중 | 대기중 | 대기중 |
| `sent` | 전송됨 | 전송됨 | 전송됨 |
| `read` | 읽음 | 읽음 | 읽음 |
| `hidden_spam` | 숨겨진 요청 · 스팸 | 숨겨진 요청 · 스팸 | 숨겨진 요청 · 스팸 |
| `attention` | 확인 필요 | **전송 실패** | **전송 실패** |

`attention` 의 서버 라벨("확인 필요")과 프론트 라벨("전송 실패")이 다르지만 **그대로 둡니다** —
유저 콘솔은 프론트 i18n 을 쓰고, 서버 라벨은 **어드민이 쓰는 값**이라 건드리면 어드민 화면이
같이 바뀝니다. 초안의 "발송되지 않음" 안은 폐기했습니다.

**`hidden_spam` 의 "스팸"도 유지합니다.** 수신자에게 어디를 보라고 알려주는 정보이고,
서버·프론트가 이미 같은 단어를 쓰고 있습니다. 불안은 라벨이 아니라 **본문에서 "정상 발송됐고
실패가 아니다"를 분명히 해서** 줄입니다(§4 U4).

## 4. 사유 매핑 — 운영 24종 → 사용자 8묶음 (사유 키 9종)

왼쪽은 어드민 화면이 계속 그대로 씁니다. 오른쪽만 유저 콘솔에 나갑니다.
U8 만 **지연 / 종결** 두 문구로 갈리므로 `user_reason` 키는 총 9개입니다.

---

### U1. 인스타그램 연결 해제

| 운영 사유(reason) | 운영 문구 |
|---|---|
| `connection_lost` (code 190) | Instagram 연결이 끊김 |
| `session_expired` (code 102) | Instagram 연결이 끊김 (세션 만료) |
| `token_invalid` (failed_token) | Instagram 연결이 끊겨 보내지 못함 |


**다섯 사유를 한 문구로 통합합니다.** 뒤 두 개는 내부 대기열 사정이지만, 사용자에게 유효한

```
제목      댓글을 삭제했거나 작성된 지 7일이 초과되었어요

CTA       없음                          심각도  info
```
> **어드민에서는 계속 다섯으로 갈라져 있습니다.** `stalled_by_us` 가 늘어나는 것은 발송
> 파이프라인 이상 신호라 운영자에겐 반드시 구분돼야 합니다 — 유저 화면에서만 합칩니다.
>
> "설정과 무관합니다" 같은 문장도 넣지 않습니다. 원인을 말하지 않기로 한 이상 **확인하라는
> 암시도 함께 빼야** 합니다(§2-3 하단). 다음 행동은 "조치하실 일 없음" 하나입니다.
>
> ⚠️ **확인 부탁드립니다(§6-⑩) — 이 버킷에 7일이 아닌 건이 섞입니다.** 제목·이유가 "댓글
> 작성 후 7일"만 말하는데, **스토리 답장 트리거와 후속 DM 은 창이 24시간**입니다(댓글이 아니라
> 마지막 대화 기준). 그 건이 이 사유로 종결되면 화면에는 "댓글 작성 후 7일"이라고 뜹니다.
> 스토리 답장 캠페인을 쓰는 고객에게는 맞지 않는 안내가 됩니다.
> 세 가지 중 고르시면 됩니다 — (a) 그대로 두기(스토리 답장 비중이 낮다면 감수)
> (b) 제목을 **"댓글을 삭제했거나 발송 가능 시간이 지났어요"** 로 되돌리고 7일은 이유에만 두기
> (c) U3 를 **댓글 기반 / 대화 기반** 두 문구로 분리. **(b)를 권합니다** — 제목은 두 경우를
> 모두 덮고, 흔한 쪽(7일)의 구체적 설명은 이유에 그대로 남습니다.

### 표에서 읽을 때 주의

- **`other` 를 빼면 심각도가 전부 `info`** 입니다 — 건너뜀은 status 가 `skipped` 하나뿐이라
  status 기준 심각도가 같습니다(결정 ④ 로 이번 라운드에서 색을 안 바꿨기 때문).
  `monthly_dm_limit` 처럼 조치가 필요한 건도 회색으로 뜹니다. 사유별로 색을 가르려면 프론트가
  배지를 `user_reason` 기준으로 그린 뒤(UC-6) 서버가 심각도를 사유 기준으로 옮겨야 합니다.
- **`other` 만 `warning` 예외**(2026-08-07 결정) — 우리도 원인을 모르는 유일한 건이라 파란
  `info` 로 두면 "정상 처리"처럼 읽힙니다. 사용자가 문의해야 하는 유일한 건너뜀이라 주황·경고
  아이콘으로 띄웁니다. 목록 배지는 아직 status(=회색) 기준이라 **헤더만 주황**이 되지만,
  실데이터 0건이라 영향 범위가 사실상 없습니다. 구현은 `_SEVERITY_BY_USER_REASON`.
- **CTA 가 전부 비어 있습니다** — 플랜 변경·캠페인 켜기 같은 버튼을 넣고 싶었지만, 프론트
  `handleCtaClick` 이 `reverify`/`retry`/`ig_reconnect` 만 처리해서 **모르는 action 을
  내려보내면 눌러도 아무 일 없는 버튼**이 됩니다. 핸들러가 붙으면 그때 서버에서 추가합니다.

> **`messaging_window_skip` 은 2026-08-07 에 새로 등록**했습니다 — dev 실측에서 `other`(미분류)로
> 떨어지던 건을 조사하니 `24h 메시징 윈도우 밖` 이라는 알려진 사유였습니다. 어드민 사전
> (`SKIPPED_REASONS`)에도 함께 넣어 '기타(조사 필요)' 대신 정식 행으로 뜨게 했습니다.
>
> **`other` 는 사유가 아니라 미분류**입니다 — 건너뜀은 `error_message` 문자열로 사유를 가리는데,
> 위 9종 어디에도 안 걸리면 여기로 옵니다. 운영 대응 스크립트가 임의 문구를 찍었거나, 새 코드
> 경로가 사전에 없는 문구를 쓰기 시작했다는 신호라 **어드민에서는 유일하게 `investigate`(조사
> 필요)** 로 잡힙니다. 실제로 그 신호 덕에 위 `messaging_window_skip` 을 찾았습니다.
> (dev 실데이터 기준 현재 `other` **0건** — 그래서 더미 카탈로그에 일부러 한 건 넣어 뒀습니다.)
>
> ⚠️ 그래서 `other` 문구는 **원인을 지목하면 안 됩니다.** 예전 문구("설정이나 계정 상태에 따라")는
> 우리가 모르는 것을 아는 척한 것이라 §2-4 위반이었습니다 — 사용자가 없는 원인을 찾으러 갑니다.
> 지금은 원인을 말하지 않고 문의로 유도합니다. 또 `other` 는 status 가 `skipped` 지만 화면
> 그룹은 **attention("전송 실패")** 이라, 문구도 "건너뜀"이 아닌 실패 화법으로 맞췄습니다.
>
> **뒤 두 정리 건에서 "운영팀이 확인 후 정리"를 뺐습니다** — 사람이 수동으로 개입했다는 사실은
> §2-3 ③ 에 해당하고, "무슨 일이 있었길래 사람이 손댔지" 하는 의문만 남깁니다.
>
> `monthly_dm_limit` 은 **유저가 지금 전혀 모르는 상태**입니다 — 조용히 건너뛰어지고 알림은
> 내부 채널로만 갑니다. 문구뿐 아니라 알림이 필요합니다
> ([`USER_NOTIFICATION_PLAN.md`](USER_NOTIFICATION_PLAN.md) N-4).
> "다시 발송돼요"는 약속해도 됩니다 — `revive_quota_skipped_dms` 가 유료 전환 시 자동
> 발동하도록 배포돼 있습니다. 다만 발송 가능 시간을 넘긴 건은 되살릴 수 없어
> **"댓글 작성 후 7일 이내"** 단서가 반드시 필요합니다.

## 7. 구현 방식 제안 (결정 ⑥)

지금은 서버가 **완성된 한국어 문장**을 내려줍니다. 그래서 ①영어 지원이 안 되고 ②문구 수정에
백엔드 배포가 필요하고 ③프론트가 못 참으면 덮어쓰게 됩니다(§1-2).

**제안: 서버는 `user_reason`(머신 키)만, 문구는 프론트 i18n.**

```jsonc
// GET /integrations/dm-verification/logs/ 응답의 frontend_action (제안)
"frontend_action": {
  "user_reason": "connection_lost",     // ★ 신규 — U1~U8 · S1~S8 의 머신 키
  "severity": "error",
  "cta": { "label_key": "dmAuto.cta.reconnect", "action": "ig_reconnect" },
  "checklist": [ { "id": "recipient_account" }, { "id": "ads_restriction" },
                 { "id": "other_dm_tool" } ],       // id 만 · 배열 순서 = 표시 순서
  // ↓ 하위호환 — 한 라운드 병행 유지 후 제거
  "title": "...", "description": "..."
}
```

**i18n 키는 §2-1 의 세 부분을 그대로 따릅니다** — 프론트가 임의로 합치면 구조가 무너지므로
키 자체를 나눕니다.

```jsonc
"dmAuto.reason.connection_lost": {
  "title": "인스타그램 계정 연결이 해제되어 발송되지 않았어요",
  "cause": "인스타그램 설정에서 연결이 해제되었거나, … 자동 DM 발송이 모두 중단돼요.",
  "next":  "다시 연결하시면 이후 작성되는 댓글부터 발송이 재개돼요. …"
}
```

- **`scope` 키는 두지 않습니다** — 범위가 필요한 사유는 `cause` 안에 문장으로 넣습니다(§2-1).
- 서버는 **분류만** 소유합니다. `user_reason` 은 운영 `reason` 24종 위에 얹는 **접기 층**이며,
  매핑표가 §4·§5 입니다.
- **접기 매핑이 이 문서의 핵심 자산입니다** — 여기서 `stalled_by_us` → 시간 경과로 접는 결정이
  곧 "내부 사정을 유저에게 안 보인다"의 구현입니다. 어드민 사전은 그대로 둡니다.
