# [백엔드 → 프론트] iOS IG 연동 실패 — prod 실측 증거와 재설계 요청

작성 2026-09-03 · CS #6fa086bd 조사 결과 · 선행 문서 [`IG_OAUTH_RETURN_TO_FRONTEND.md`](./IG_OAUTH_RETURN_TO_FRONTEND.md)(2026-08-04)

**한 줄:** 8-04 라운드에서 합의한 `return_to` 는 **결과 전달만 고쳤고, 원인(authorize URL 납치)은
그대로**입니다. 이번엔 추측이 아니라 **실측 데이터**가 있습니다 — 한 고객이 **16시간 동안 73번
시도해서 3번 성공**했습니다.

이 문서는 **관측된 사실과 그 경계**를 넘기는 것이 목적입니다. iOS 동작 검증과 해법 설계는
프론트에서 맡아 주시고, 백엔드가 뭘 바꿀지는 §5 에 적었습니다.

## 1. 무슨 일이 있었나

프로 플랜 고객(`crocsjs@gmail.com`, ws `5f52c193`)이 인스타그램 연동이 안 된다고 문의했습니다.
문의 원문:

> **"인스타그램이 로그인 되어 있는데 연동 불가 입니다.ㅠㅠ"**

이 한 문장이 증상을 정확히 묘사하고 있었다는 게 조사 결론입니다(§4).

기기는 **전 시도가 iPhone Safari (iOS 18.7)** 이고, 모든 요청이 `return_to` 를 붙여
보내고 있었습니다. 즉 **8-04 에 합의한 모바일 경로를 정상적으로 타고 있었는데도 실패**했습니다.

## 2. 실측 — 성공률 4%

`connect/start` 호출 73회 대비, 인스타그램이 우리 콜백으로 돌아온 것은 **4회**뿐입니다.

```
connect/start (POST)          73
콜백 도달                       4      ← 5.5%
실제 연동 성사                   3
```

### 측정 방법 (재현 가능)

`IGOAuthState` 행은 **연동 성공 직전에만 삭제**됩니다(만료 정리 배치 없음). 따라서
`DB에 남은 state = 콜백이 안 온 시도` 입니다.

- 이 워크스페이스의 잔존 state: **69개**
- 접속로그의 콜백 state: 59개
- **교집합: 0** (동일 방식으로 알려진 state 를 조회해 sanity check 통과)
- 73(시도) − 69(무응답) = **4(콜백 도달)** — 정확히 일치

### 콜백까지 간 4건의 정체

| 탭 시각(KST) | 기기 | 콜백 복귀 | **소요** | 결과 |
|---|---|---|---|---|
| 09-02 19:55:49 | **PC (Edge)** | 19:56:34 | **45초** | `crocs_jamsil_` 연동 ✅ |
| 09-02 19:56:59 | PC (Edge) | 19:57:06 | 7초 | (중복 콜백) |
| 09-02 22:06:03 | iPhone | 22:10:00 | **3분 57초** | `kangaroo.7235829` 연동 ✅ |
| 09-03 11:59:15 | iPhone | 12:03:58 | **4분 43초** | `crown550190` 연동 ✅ |

**PC 는 첫 시도에 45초로 끝났습니다. 아이폰은 71번 중 2번입니다.**

### 사용자가 실제로 겪은 것

```
09-03 10:20:31  탭
09-03 10:20:33  탭   ← 2초 뒤
09-03 10:20:53  탭
09-03 10:21:01  탭
09-03 10:21:03  탭   ← 2초 뒤
09-03 10:25:13  탭
...
09-03 10:22     고객센터 문의 접수      ← 이 시점까지도 계속 실패 중
...
09-03 11:59:13  탭 → 실패
09-03 11:59:15  탭 → ✅ (4분 43초 뒤 복귀)
```

**화면에 아무 반응이 없으니 초 단위로 연타**하고 있습니다. 이 연타 자체가
"현재 UI 가 실패를 사용자에게 알려주지 못한다"는 증거입니다(§6-2).

## 3. 확정된 사실 / 추론 — 경계를 명확히 합니다

프론트에서 잘못된 전제로 조사에 시간 쓰지 않도록 구분해 둡니다.
(8-04 라운드에서 저희 낡은 문서 때문에 그런 일이 있었습니다.)

### ✅ 서버 로그로 확정된 것

1. 73번 중 69번은 **인스타그램 화면 안에서 끝났습니다.** 콜백 요청 자체가 없습니다.
2. 그 69번은 `error=access_denied`(사용자 거부) **조차 아닙니다.** 같은 시간대에 다른
   고객의 `user_denied` 콜백은 5건 찍혔지만, 이 고객 state 와는 교집합이 0입니다.
   → **사용자가 승인 화면을 보고 거절한 게 아니라, 승인 화면에 도달하지 못했습니다.**
3. 우리 백엔드 게이트(중복연동·플랜한도)는 **한 번도 실행되지 않았습니다.** 이 실패는
   백엔드 로직 문제가 아닙니다.
4. 성공한 2건의 iPhone 콜백은 **Safari UA** 로 돌아왔습니다(인스타 앱 UA 아님).

### 🔶 정황 기반 추론 (프론트 검증 필요)

5. **iOS 유니버설 링크가 `instagram.com/oauth/authorize` 를 가로채 Instagram 앱을
   띄운다** — 8-04 문서 §1 에서 이미 양측이 동의한 전제이고, 우리 코드 주석에도
   적혀 있습니다([`views.py:143-148`](../../apps/integrations/views.py#L143-L148)).
   다만 **앱이 열렸다는 건 서버 로그로 볼 수 없습니다.** 실기기 확인이 필요합니다.

6. **연타의 "두 번째 탭"이 성공했다** — 성공한 iPhone 2건이 2/2 로 이 모양입니다.

   ```
   22:05:57 탭 → 실패      11:59:13 탭 → 실패
   22:06:03 탭 → ✅        11:59:15 탭 → ✅
   ```

   ⚠️ **다만 이건 성공 조건이 아닙니다.** 둘 다 실패한 연타 쌍이 여럿 있습니다
   (`10:20:31/33`, `10:21:01/03`, `22:28:49/50`, `22:32:29/30`, `22:37:46/47`).
   → **같은 폰·같은 버튼인데 결과가 갈리는 간헐적 현상**으로 보는 게 맞습니다.
   "재탭하면 된다"를 해법으로 삼지 마세요.

## 4. 소요시간이 알려주는 것 — 문의 문구의 정체

45초(PC) vs 약 4분(iPhone 성공 2건)의 차이는 **인스타 로그인 화면을 통과했는지** 입니다.

- **PC**: Edge 세션에 인스타 로그인됨 → 승인 버튼만 → 45초
- **iPhone 성공 2건**: **Safari 에는 인스타 로그인 세션이 없어서** authorize 페이지가
  아이디·비밀번호(+2단계 인증) 입력을 요구 → 폰으로 타이핑 → 약 4분

그런데 **Instagram 앱에는 로그인이 되어 있습니다.** 이 둘을 합치면:

> 탭 → iOS 가 Instagram **앱**을 띄움 → 앱은 이미 로그인 상태 → 사용자 눈엔
> "인스타 로그인 잘 되어 있는데?" → 그런데 연동은 진행되지 않음 → 콜백 0

**"인스타그램이 로그인 되어 있는데 연동 불가"** 는 정확히 이 상태입니다.
앱에는 로그인돼 있고, 정작 인증이 일어나야 할 **Safari 에는 로그인이 안 되어 있던** 것.

이게 맞다면 시사점이 하나 더 있습니다 — **"인스타 앱에 로그인돼 있으면 오히려 더 잘
실패한다"** 는 뜻이라, 로그인 안내로는 해결되지 않습니다.

## 5. 백엔드가 할 일 (프론트 작업과 독립)

| 항목 | 내용 | 프론트 영향 |
|---|---|---|
| `force_reauth=true` 추가 | authorize URL 파라미터. Meta 문서: *"true 면 이미 인스타그램에 로그인되어 있어도 프로페셔널 계정 자격증명으로 다시 로그인하도록 강제"*, *"로그인 페이지는 미로그인 상태이거나 `force_reauth` 가 전달된 경우에만 표시"* | **없음** (URL 값만 바뀜) |
| 연동 시도 계측 | `IGOAuthState` 에 소비/실패 사유가 안 남아, 이번 조사에 접속로그 대조가 필요했습니다. 결과를 기록하도록 고칩니다 | 없음 (§7 측정에 사용) |

### `force_reauth` 가 고치는 것 — 이번 건의 **두 번째 문제**

지금은 파라미터가 없어 **계정 선택 화면이 통째로 생략되고, 세션에 물린 계정이 그대로
연결**됩니다. 이 고객이 실제로 겪은 일:

```
09-02 22:09:59  kangaroo.7235829 연동됨
09-02 22:10:19  20초 뒤 본인이 해제      ← 원하는 계정이 아니었음
```

⚠️ **`force_reauth` 는 §2 의 성공률 4% 문제를 고치지 못합니다.** 유니버설 링크 납치는
그대로입니다. 별개 문제의 별개 수정입니다.

## 6. 프론트에 넘기는 요구사항

구현 방식은 그쪽 판단에 맡깁니다. **충족해야 할 조건**만 적습니다.

### 6-1. (핵심) authorize URL 이 Safari 안에서 열리게 할 것

8-04 §1 에서 확인된 제약이 그대로 유효합니다:

- authorize 호스트는 **`www.instagram.com` 하나뿐**입니다. 대체 호스트로 못 피합니다.
- `return_to` 는 **결과 전달** 문제만 고쳤습니다. 이번 실측이 그 증거입니다.

**우리가 검증하지 않은 후보들**입니다. 실기기 확인은 프론트에서 부탁드립니다:

- JS `window.location` 대신 **사용자가 직접 탭하는 `<a>` 링크**로 전환
  (iOS 는 JS 유발 내비게이션과 사용자 제스처 링크 탭의 유니버설 링크 처리가 다릅니다)
- `target="_blank"` / 새 탭
- 우리 도메인의 **중간 안내 페이지**를 띄우고 거기서 "인스타그램으로 이동" 을 탭하게 하기
- iOS 감지 시 **PC 연결 유도**(QR 핸드오프 등) — 실측상 PC 는 45초·1회 성공이라
  가장 확실한 우회로입니다

> 어느 것도 저희가 확인하지 못했습니다. **하나 고르기 전에 실기기에서 재현부터** 해주세요
> (아이폰 + Instagram 앱 로그인 상태 + Safari 인스타 미로그인 = 재현 조건으로 추정).

### 6-2. 실패를 사용자에게 보이게 할 것

지금은 **탭해도 아무 일이 안 일어나고**, 그래서 초 단위로 연타합니다(§2). 최소한:

- 돌아오지 않으면 **타임아웃 후 명시적 실패 안내** (8-04 때 잡으신 "타임아웃 없어 이후
  버튼 무반응" 버그와는 별개로, 이번엔 *사용자에게 보이는 메시지*가 필요합니다)
- 안내에 **PC 로 연결하기** 대안 포함
- **연타 방지** — 진행 중에는 버튼 비활성. 지금은 2초 간격 5연타가 그대로 서버에 옵니다

### 6-3. 계정이 여러 개인 사용자 안내

`force_reauth` 로 계정 선택 화면은 뜨게 되지만, **프로 플랜은 IG 계정 1개**입니다.
연동 화면에서 현재 사용량(예: `1/1`)과 "다른 계정을 붙이려면 기존 연결 해제 필요" 를
미리 보여주면 이 유형의 문의가 줄어듭니다.
(참고: [`IG_ACCOUNT_ACTIVATION_FRONTEND.md`](./IG_ACCOUNT_ACTIVATION_FRONTEND.md))

## 7. 완료 판정 — "고쳤다"를 무엇으로 말할 것인가

이번 건은 **고객이 69번 실패한 뒤 우연히 통과**했고, 서버 로그를 뒤지기 전까지는
해결됐는지조차 몰랐습니다. 같은 일이 반복되지 않으려면 숫자가 필요합니다.

**주 지표: 콜백 도달률 = `콜백 수 / connect/start 수`**

| | 값 |
|---|---|
| 현재 (이 고객, iOS) | **4 / 73 = 5.5%** |
| 현재 (같은 고객, PC) | 2 / 2 |
| 목표 | iOS 에서 **80% 이상** |

백엔드가 §5 의 계측을 넣으면 워크스페이스·기기별로 이 값을 뽑아 드릴 수 있습니다.
배포 후 며칠치 수치를 같이 보고 판정하시죠.

**보조 지표**

- 한 워크스페이스의 **10분 내 `connect/start` 5회 이상** 발생 건수 → 0 에 수렴해야 함
  (연타 = 사용자가 실패를 인지 못 하는 상태의 대리 지표)
- 연동 성사까지 걸린 시간 — PC 45초가 기준선입니다
