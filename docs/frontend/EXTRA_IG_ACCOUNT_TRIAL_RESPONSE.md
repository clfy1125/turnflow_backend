## 요청 6건에 대한 답

### 1. [필수] 에러 포맷 각주 정정 + envelope 통일 계획 → **문서 정정 + 코드도 고쳤습니다**

v1 각주가 틀렸습니다. 지적하신 대로 `BillingFlowError` → `{detail}`, 시리얼라이저
`ValidationError` → envelope 두 갈래였습니다. 원인은 `_flow_error_response` 가 **DRF 예외
핸들러를 우회해 Response 를 직접 만들던 것**입니다 — CLAUDE.md §6("응답을 직접 만들 때도 이
포맷 유지") 위반이 오래 방치돼 있었습니다.

**통일 계획을 묻지 않고 지금 처리했습니다.** 정책 거절 4xx 이 이제 **두 포맷을 동시에** 냅니다:

```jsonc
{
  "detail": "미납 상태에서는 추가 계정을 구매할 수 없습니다. 결제 수단을 확인해주세요.",
  "success": false,
  "error": { "code": 400, "message": "미납 상태에서는 추가 계정을 구매할 수 없습니다. …" }
}
```

- `detail` 은 **영구 유지**합니다 — 기존 프론트·앱이 읽고 있어 지우면 결제 화면 문구가 한 번에
  사라집니다. 나중에 `detail` 을 없애는 계획은 **없습니다.**
- 4xx 에만 붙습니다. 202(결제 확인 중)에는 안 붙습니다.
- 402 의 `toss_code` 등 부가 필드는 같은 바디에 그대로 옵니다.
- billing 전 엔드포인트(confirm · change-plan · cancel · extra-accounts …) 공통입니다.
- 회귀 테스트로 못 박았습니다 (`test_policy_rejection_carries_both_error_formats`).

`parseApiDetail` 이 세 자리를 다 읽게 고치시는 방향 그대로 가 주세요 — 그게 어느 포맷이 와도
안전한 쪽이고, 이제는 어느 쪽을 읽어도 채워져 있습니다.

### 2. [필수] dev 테스트 카드 → **실측 목록 드립니다** (문서 v2 §5)

`433012…` 실패 재현했습니다. 후보 BIN 을 훑어 통과하는 것만 남겼습니다.

| 카드번호 | BIN |
|---|---|
| `3562951111111111` | 356295 |
| `3562961111111111` | 356296 |
| `3562971111111111` | 356297 |
| `9490011111111111` | 949001 |

`card_expiration_month: "12"` / `card_expiration_year: "30"` / `customer_identity_number: "900101"`.

실패 확인: 433012 · 402841 · 542208 · 552046 · 435760 · 356355 · 424321 · 519014 ·
400200 · 456524 · 431196 · 465817 (`NOT_SUPPORTED_CARD_TYPE`), 940101(`INVALID_CARD_NUMBER`).
토스 테스트 환경의 BIN 표가 바뀐 것으로 보입니다. 토스 문서는 "앞 6자리(BIN)만 유효하면
등록된다"고만 적어서, **"유효"가 실제 발급사 BIN 이라는 뜻**임을 읽어내기 어렵습니다.

말씀하신 대로 **전자(카드번호)** 를 골랐습니다 — 이제 임의 상태를 직접 만들 수 있으니
`billing-trialing@test.com` 하나에 매달리지 않아도 되고 세션 충돌도 사라집니다.
회원가입 → `dev/issue-billing-key/ {plan_name:"pro"}` 두 번이면 체험+카드 계정이 나옵니다.
그래도 시드 계정이 편하시면 말씀 주세요 — `seed_billing_test_accounts` 에 넣겠습니다.
Swagger 의 `[DEV] 카드번호로 빌링키 발급` 문서에도 이 표를 넣어 배포했습니다.

### 3. [확인] 체험 중 상한 없음 → **의도된 제품 결정. 감수합니다**

시나리오와 계산 모두 **맞습니다**(월 99,000원어치, 첫 결제 전 해지 시 실결제 0원).
잡아 주셔서 감사합니다. 그럼에도 **상한을 두지 않기로 결정**했습니다 — 전환율을 우선하고,
체험은 `trial_used_at` 으로 1인 1회이며 카드 등록이 필수라 완전 익명 남용은 아닙니다.
제안해 주신 1안은 채택하지 않았습니다.

결정에 쓴 prod 실측(2026-08-21):

| 지표 | 값 |
|---|---|
| `extra_ig_accounts > 0` 인 구독 | **0건** (전체 171건 전부 0) |
| 활성 IG 2개 이상 연동한 사용자 | **0명** (81명 전원 1개) |
| 체험 중 프로 구독 | 46건 |

추가 계정 기능은 **아직 실사용 0건**이고 CS #d34572b3 이 첫 구매 시도자였습니다. 지금 상한을
넣어도 기존 사용자 피해는 0이지만, **남용도 아직 0건**이라 관측되기 전에 전환 장벽을 세우지
않는 쪽을 골랐습니다. 관측되면 백엔드에 상한을 넣고 알려 드립니다 —
말씀대로 프론트 스테퍼는 우회 가능하니 방어 지점은 백엔드입니다.

→ **프론트 추가 작업 없습니다.** 상한 400 이 나갈 일이 없습니다.

### 4. [확인] `next_renewal_amount: 35700` → **오타가 아니라 옛 가격의 잔재**

프로 정가가 **15,900원이던 시절**에 쓰인 예시입니다(15,900 + 19,800 = 35,700). 지금은
정가가 14,900원이라 **34,700 이 맞습니다** — 그린 시안 그대로 가시면 됩니다. Swagger 예시
금액도 전부 현재 정가 기준으로 고쳐 배포했습니다(29700→34700, 9900→14900, 25800→24800).

★ 다만 **프론트에서 "정가 + 9,900×N" 으로 재계산하지 마세요.** 기준액은 플랜 정가가 아니라
그 사용자의 **가입 시점 가격 스냅샷**(`monthly_amount_snapshot`)입니다 — 그랜드파더링 때문에
같은 프로라도 9,900 / 15,900 / 14,900 이 섞여 있습니다. 서버가 준 `next_renewal_amount` 를
그대로 표시해 주세요.
