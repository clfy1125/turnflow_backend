## 2. 알림 원칙 (남발 방지)

**문구 작성 기준은 [`DM_USER_COPY_MAPPING.md`](DM_USER_COPY_MAPPING.md) §2 를 그대로 따릅니다**
(**현재 상태 → 발생 이유 → 다음 행동** / 탓하지 않기 / 단정하지 않기 / 내부 사정 비노출).
알림은 화면보다 맥락이 적은 상태로 도착하므로, **범위를 모르면 오해가 생기는 경우**
(예: "이 계정만인지 전체인지")는 이유 문장 안에 함께 적습니다.

알림 발생 기준은 아래를 통과하는 것만 만듭니다 — 알림은 **켜기보다 끄기가 어렵습니다.**

1. **행동 가능하거나, 돈이 걸렸을 때만** — "알아두면 좋은 것"은 알림이 아니라 화면에 둡니다
2. **같은 사건은 하루 1회** — 상태 기반 사건(연결 끊김)은 **해소될 때까지 반복 금지**
3. **인앱이 먼저, 이메일은 이탈했을 때** — 콘솔에 들어와 있으면 배너로 충분
4. **거래성 / 광고성 구분** — 정보통신망법상 서비스 장애·결제 알림은 **동의 불필요**,
   기능 홍보·업셀은 `marketing_opt_in` 필요.
   ⚠️ **"한도 다 썼으니 업그레이드하세요"는 경계선입니다** — 장애 고지 + 해결책 제시로
   구성하면 거래성, 할인·프로모션을 얹으면 광고성입니다 (§6-③)
5. **해소도 알린다** — 연결이 복구됐으면 그것도 알려야 유저가 화면을 다시 안 뒤집습니다

## 4. 채널 설계 제안

### 4-1. 인앱 배너 = **상태 기반**(이벤트 아님)

N-1·N-2·N-3·N-4·N-11 은 전부 **"지금 이 상태인가"** 로 판정됩니다. 알림 테이블에 이벤트를
쌓는 대신 **현재 상태를 계산해 내려주는 엔드포인트 하나**가 더 단순하고, 해소 시 자동으로
사라집니다(N-15 가 공짜로 해결됨).

```jsonc
// GET /api/v1/me/alerts/   (제안 · 신규)
{
  "alerts": [
    {
      "code": "IG_DISCONNECTED",          // 머신 키 — 문구는 프론트 i18n
      "severity": "critical",             // critical | warning | info
      "scope": "workspace",               // workspace | ig_connection | campaign
      "target_id": "…",                   // scope 대상 (있으면)
      "cta": { "action": "ig_reconnect" },
      "since": "2026-08-05T10:00:00+09:00",
      "dismissible": false                // critical 은 못 닫음
    }
  ]
}
```

- 판정 소스는 **이미 있는 것들을 재사용**: `connection_health` · `check_dm_quota` ·
  `UserSubscription.status` · `ig_activation_review_needed` · `queue_state.blocking_reason`
- 폴링 30~60초 또는 화면 진입 시 1회. 캐시 30초.
- **새 모델 없음 / 마이그레이션 없음** — 파생 계산만.

### 4-2. 이메일 = **이탈했을 때만**

인앱 배너로 이미 보고 있는 유저에게 메일까지 보내면 피로합니다. 제안:

> 배너 발생 후 **24시간 동안 콘솔 접속이 없으면** 이메일 1회.
> (`User.last_login` 또는 API 접근 시각 기준)

이러면 신규 메일 템플릿은 **4종**이면 충분합니다:
`ig_connection_lost` · `dm_quota_reached` · `trial_ending` · `token_expiring`

### 4-3. 알림 이력이 필요해질 때

"지난주에 무슨 일이 있었나"를 유저가 봐야 할 때가 오면 그때 이벤트 테이블을 만듭니다.
**지금은 필요 없습니다** — 상태 배너로 P0/P1 의 대부분이 덮입니다.
