# 연령 제한 게시물 — 「차단」이 아니라 「지연」입니다 (프론트 변경 요청)

**작성 2026-10-13 · 백엔드 변경 완료(미배포) · 마이그레이션 없음 · 새 엔드포인트 없음**
**기존 응답 키는 하나도 지우지 않았습니다(병기만).**

---

## 0. 세 줄 요약

1. 인스타가 '연령 제한 콘텐츠'로 분류한 게시물에서 **자동 DM 발송이 다시 됩니다.**
   (2026-09 중순부터. prod 실측 **12,539건 중 실패 0건**)
2. 다만 **댓글 웹훅이 안 와서** 서버가 1시간마다 댓글을 훑어 보냅니다 → DM이 **최대 1시간 지연**.
   고객이 "처음엔 가다가 멈췄어요"라고 하는 증상이 정확히 이것입니다.
3. 그래서 프론트에서 **① `state === "restricted"` 로 버튼을 막으면 안 되고(치명적)**
   **② 새 `delay_notice` 를 노란 배너로 그려야** 합니다.

---

## 1. 배경 — 무엇이 바뀌었나

2026-09-04 부터 인스타가 게시물을 '연령 제한 콘텐츠'로 분류하면 **세 가지가 동시에** 일어났습니다.

| | 2026-09 초 | **2026-10 현재** |
|---|---|---|
| 로그아웃·미성년에게 비노출 | O | O (그대로) |
| 댓글 웹훅 미전송 | O | **O (그대로 — 이게 지연의 원인)** |
| 비공개 답장(DM) 거부 | O (60~100% 실패) | **X — 발송 성공** |

**근거(prod 실측, 2026-10-13)**

- 현재 제한 확정 게시물 13개에 최근 10~14일간 오프닝 DM **12,539건 / 거부(2534066) 0건 / 성공 96.8%**
- 제한 여부는 공개 페이지의 `gating_ruling` 객체로 확인(제한 713~720KB vs 정상 925~961KB) — **13/13 일치**
- 폴링으로 들어온 DM 중 마지막 거부는 **2026-09-16**. 그 뒤 9,000여 건 전부 성공.
- 경쟁사(NHN 소셜비즈)는 아직 "제한 게시물은 DM 미발송"으로 안내 중입니다 — 공개된 기록이 없는,
  우리 데이터로만 확인한 변화입니다.

> ⚠️ Meta 가 공지한 변화가 아니라 **관측된 동작**입니다. 되돌아갈 수 있으므로 서버가 감시 중이고,
> 되돌아가면 서버가 자동으로 다시 `blocking=true` 를 내려줍니다. 프론트는 플래그만 따르면 됩니다.

## 2. ⚠️ 치명적 — `state` 로 버튼을 막지 마세요

기존 가이드에 이렇게 적혀 있었고, **그게 이제 틀렸습니다**:

```
| restricted | 제한 확정 | 생성 버튼 비활성 + 안내 |     ← ❌ 더 이상 이렇게 하면 안 됩니다
```

**바뀐 계약**

```js
// ❌ 하지 마세요 — 잘 나갈 캠페인을 막고 "다른 게시물로 만드세요"라고 반대로 안내하게 됩니다
if (data.restriction.state === "restricted") disableCreateButton();

// ✅ 이렇게 하세요
if (!data.can_create_campaign) disableCreateButton();   // == restriction.blocking
```

- `state` = **인스타가 어떻게 분류했는가** (사실 진술)
- `blocking` = **우리가 생성을 막는가** → 그 게시물에서 **실제로 발송이 실패한 이력**이 있을 때만 `true`

그래서 **`state="restricted"` + `blocking=false`** 라는 조합이 이제 정상적으로 존재합니다.
(이게 지금 prod 에서 DM 이 잘 나가고 있는 13개 게시물의 상태입니다.)

> 백엔드도 같은 기준으로 고쳤습니다 — 생성/활성화 게이트(409)가 `state` 가 아니라 `blocking` 을
> 봅니다. 서버가 안 막는데 프론트만 막으면 **고객은 버튼이 죽은 이유를 영영 알 수 없습니다.**

## 3. 새 필드 — `webhook_silent` / `delay_notice`

`restriction` 블록에 **두 키가 추가**됐습니다. 기존 키는 그대로입니다.

| 필드 | 타입 | 뜻 |
|---|---|---|
| `webhook_silent` | `boolean` | 이 게시물의 댓글 웹훅이 끊겼는가 (= 실시간 발송 불가) |
| `delay_notice` | `object` 또는 `null` | `webhook_silent=true` 일 때만 채워짐 |
| `delay_notice.reason` | `string` | 머신 키. 현재 `"webhook_silent"` 하나 |
| `delay_notice.max_delay_minutes` | `number` | 최대 지연(분). 현재 `60` |
| `delay_notice.user_message` | `string` | **화면에 그대로 쓸 한국어 문구** |

### 그릴 곳과 색

| 상태 | 조건 | 색 | 동작 |
|---|---|---|---|
| 차단 | `blocking === true` | 🔴 빨강 | 생성/활성화 버튼 비활성 + `user_message` |
| **지연** | `blocking === false && delay_notice` | 🟡 **노랑** | **버튼 정상**, 안내만 |
| 정상 | 그 외 | — | 아무것도 표시 안 함 |

```js
const r = data.restriction;
if (r.blocking)            showBlockingBanner(r.user_message, r.next_steps);
else if (r.delay_notice)   showWarningBanner(r.delay_notice.user_message);
```

### ⚠️ 문구는 하드코딩하지 마세요

`user_message` 는 같은 `state="restricted"` 라도 **상황에 따라 서버가 다른 문장을 줍니다.**

- 발송이 막힌 경우: "…댓글 자동 DM을 보낼 수 없습니다."
- 발송은 되는 경우: "…자동 DM 발송 자체는 현재 정상이며, DM이 **최대 1시간 늦게** 도착할 수 있습니다."

프론트가 `state` 보고 문구를 지어내면 **없는 장애를 고지**하게 됩니다.
`next_steps` 도 마찬가지로 서버가 상황에 맞게 바꿔 줍니다("다른 게시물로 만드세요" vs
"캠페인은 그대로 두셔도 됩니다").

## 4. 호출 방법 (변경 없음 — 기존 엔드포인트 그대로)

### 캠페인 만들기 전

```
GET /api/v1/integrations/auto-dm-campaigns/inspect-media/
      ?workspace_id={ws}&media_id={mediaId}&permalink={encoded}
```

### 이미 만든 캠페인

```
GET /api/v1/integrations/auto-dm-campaigns/{id}/inspect/
```

둘 다 **우리 DB 만 읽습니다 — 인스타 API 쿼터를 쓰지 않습니다.** 항상 200(report-only).
캠페인 상세 화면 진입 시 호출해도 비용 문제 없습니다.

## 5. CS 대응 문구 (그대로 써도 됩니다)

> "DM이 안 가는 게 아니라 **늦게 가는** 상태입니다. 인스타그램이 이 게시물을 연령 제한
> 콘텐츠로 분류하면 댓글 알림을 저희에게 보내주지 않습니다. 그래서 저희 서버가 1시간마다
> 댓글을 다시 확인해 발송합니다 — **빠지는 분 없이 전부 나가지만 최대 1시간 걸립니다.**
> 즉시 발송을 원하시면 제한되지 않은 새 게시물로 캠페인을 하나 더 만들어 주세요.
> 게시물이 제한됐는지는 **시크릿 창(로그아웃)에서 게시물 링크를 열어** 확인하실 수 있습니다."

## 6. 안 해도 되는 것 (명시)

- ❌ 새 엔드포인트 연동 — 없습니다
- ❌ 기존 키 제거 대응 — 하나도 안 지웠습니다(`state`·`source`·`user_reason`·`blocking`·
  `user_message`·`how_to_check`·`next_steps`·`evidence` 전부 유지)
- ❌ 폴링 주기·재시도 로직 — 전부 서버 몫입니다
- ❌ "제한 여부 직접 확인" — 인스타 공개 페이지를 프론트에서 긁지 마세요(CORS·차단)

## 7. 아직 안 만든 것 — 결정이 필요합니다

**캠페인 목록/상세에 `webhook_silent` 를 인라인으로 넣지 않았습니다.** 지금은 점검 API 를
호출해야 알 수 있습니다. 목록에 넣으려면 행마다 장부 조회가 붙어 N+1 이 되므로, 필요하면
말씀 주세요 — 집계를 한 번에 거는 방식으로 따로 내리겠습니다.

마찬가지로 **홈 알림(`/home/alerts/`)에 "이 캠페인 DM이 지연 중" 카드를 넣지 않았습니다.**
홈은 전 사용자 첫 화면이라 알림 추가는 제품 결정 사항입니다.

## 8. 백엔드가 같이 고친 것 (참고 — 프론트 작업 없음)

1. **폴러가 활성 게시물의 47%를 안 보고 있었습니다.** 상한 1,000개에 "최신순" 정렬이 얹혀
   1,873개 중 873개가 영구 제외였고, 조용히 잘려서 아무도 몰랐습니다. 활동성 기준 선정으로
   바꿔 **전수 커버리지**가 됐습니다(7일 내 댓글이 있는데 폴링을 못 받던 타깃 191개 구제).
2. **잘리면 Telegram 으로 웁니다.** 이 결함이 안 보였던 이유가 "잘려도 아무 말을 안 해서"였습니다.
3. **라이브 제한 점검을 켜도 멀쩡한 캠페인이 409 로 막히지 않습니다**(위 §2 의 서버 쪽 대응).
