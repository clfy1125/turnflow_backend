## 1. OPS-5 — 제거했습니다

**다른 소비자가 없습니다.** 레포 전체에서 `action_required` 를 읽는 코드는 테스트뿐이었고
(배치·알림·내부 대시보드 어디에도 없음), 그래서 **응답 계약에서도 필드를 아예 뺐습니다.**
zod 에서 이미 빼셨다고 하셨으니 프론트는 그대로 두시면 됩니다.

함께 사라진 계산 — 30초마다 돌던 것들입니다.

- 항목 9종의 개별 집계
- **`QUEUED` 상위 2000행을 파이썬으로 순회하며 윈도우 만료를 계산하던 루프** (가장 비쌌습니다)
- `SUBMITTING` 정체 카운트, `ig_activation_review` 카운트

같은 신호가 다시 필요해지면 살아 있는 소유자가 이미 있습니다 —
`/admin/auto-dm/backlog`(윈도우 만료 임박) · `/admin/ig-connections?status=expired` ·
`/admin/users?subscription_status=past_due`. 그 목록들이 이미 필터를 갖고 있다는 점이
"여기서는 숫자만 보여 줘서 아무도 누르지 않았다"는 진단과 맞습니다.

> 참고: 이렇게 아낀 비용이 아래 OPS-7 이 추가하는 24h 집계 비용을 상쇄합니다. 두 건을 같이
> 처리한 이유입니다.

## 2. OPS-6 — 🔴 프론트 공식이 이미 8배 어긋나 있었습니다

`pending_total` 을 넣었습니다. **그런데 "지금 배포 기준으로는
`accepted_pending + queued + submitting` 과 같은 값이어야 한다"는 전제가 틀렸습니다.**
"값이 다르면 저희가 모르는 진행 중 상태가 있다는 뜻이니 알려달라"고 하셨는데, **정확히 그
경우입니다.**

### 무엇이 빠져 있었나

DM 상태 그룹의 단일 소스(`apps/integrations/dm_status_groups.py`)에서 '대기중'은 넷입니다.

```
queued · submitting · rate_limited · pending(legacy)
```

프론트 공식은 뒤의 **`rate_limited` 와 legacy `pending` 을 빠뜨리고**, 대신 `accepted`(=
'전송됨' 그룹)를 넣고 있었습니다. 두 상태는 `requested` 에는 잡히는데 **다른 어느 KPI 에도
안 잡히는 투명 상태**였습니다 — OPS-1-b 에서 잡았던 legacy `failed_api` 와 같은 종류의 구멍입니다.

dev 실데이터로 재보면:

| | 건수 |
|---|---|
| 프론트 공식 (`accepted + queued + submitting`) | **2** |
| 실제 미종결 | **16** |
| 그중 `rate_limited` 하나만 | 14 |

화면이 "대기 2건"으로 보여주는 동안 실제로는 16건이 떠 있었습니다.

### 내려드리는 것

```jsonc
"dm_quality": {
  "accepted_pending": 1,
  "queued": 2,
  "submitting": 3,
  "rate_limited": 4,     // ← 신규
  "legacy_pending": 5,   // ← 신규
  "pending_total": 15    // ← 신규 = 위 다섯의 합
}
```

구성 필드를 함께 내려 **합이 눈으로 검산되게** 했습니다. 기존 세 필드는 요청대로 그대로 둡니다.

- 정의: **요청은 만들어졌고 아직 성공으로도 실패로도 종결되지 않은 건수.**
  요청서에 적어주신 정의 그대로입니다(`accepted` 포함 — Meta 가 접수만 했고 도착이
  확정되지 않아 `delivered`/`read` 로도, `failed_no_trace` 로도 갈 수 있습니다).

### ⚠️ 라벨을 '대기' 로 두지 마세요

요청서의 **라벨('대기')과 정의('아직 결과가 안 난')가 서로 다른 것**을 가리킵니다. 이게
그대로 나가면 다음이 어긋납니다.

```
KPI '대기' 칸            → pending_total = 15   (미종결)
그 칸을 눌러 로그 목록   → ?status_group=waiting = 14  (accepted 제외)
```

`status_group=waiting` 은 "아직 Meta 미접수"라 `accepted` 를 뺍니다. 두 수가 다른 것이
**정상**인데, 라벨이 같으면 버그로 보입니다. **'진행 중'** 정도를 권합니다. 그대로 '대기'로
가시려면 드릴다운을 `?status_group=waiting` 이 아니라 미종결 전체로 맞춰야 하는데, 그 필터는
아직 없습니다 — 필요하시면 요청 주세요.

배포 전까지 프론트 폴백은 지금처럼 두셔도 됩니다(값이 작게 나올 뿐 깨지지 않습니다).

## 3. OPS-7 — 현재 시점 기준으로 고정했습니다

**요청대로 24시간 고정**입니다. 그리고 `basis` 를 함께 내려, 프론트가 짐작으로 분기하지
않아도 되게 했습니다.

```jsonc
"status_summary": {
  "basis": "now_24h",     // ← 신규. 항상 이 값
  "basis_hours": 24,      // ← 신규
  "overall": "ok",
  "subsystems": { ... }
}
```

**전체 기간을 고를 때 24h 를 한 번 더 조회하시던 것을 지우시면 됩니다.** 이제 어떤 window 를
고르든 신호등은 같은 값입니다(테스트로 고정해 뒀습니다 — `1h/24h/7d/30d` 판정 일치).

한 가지 정정: **window 종속은 부분적이었습니다.** 4개 서브시스템 중
`ig_connections` 는 원래부터 현재 시점 기준이었고, `dm` · `spam_filter` ·
`billing.failed_payments` 셋만 window 를 탔습니다. 그 셋만 24h 로 옮겼습니다.

카드·시계열(`dm_quality`, `spam`)은 **선택 범위 그대로**입니다 — 바뀐 것은 신호등뿐입니다.

> 비용: window 가 `24h`(기본 화면)면 이미 계산한 값을 재사용해 **추가 쿼리가 0** 입니다.
> 다른 window 에서만 가벼운 집계 3개가 더 나가는데, OPS-5 로 걷어낸 것보다 훨씬 쌉니다.

## 4. UI-1 — 요청 형태 그대로 만들었습니다

```
GET   /api/v1/admin/me/preferences/   → 200 { "preferences": { ... } }
PATCH /api/v1/admin/me/preferences/   ← { "mobile_nav": ["/dashboard", ...] }
                                      → 200 { "preferences": { ... } }   (병합 후 전체)
```

요청하신 네 가지를 그대로 지켰습니다.

- **스키마 검증 없음.** 서버는 JSON 을 보관하고 돌려줄 뿐 해석하지 않습니다.
- **크기 상한 4KB** (직렬화 기준). 초과 시 400 `preferences_too_large` 이며
  **기존 값은 그대로 유지**됩니다(상한 검사를 저장 전에 합니다).
- **키 단위 병합.** 보낸 최상위 키만 덮고 나머지는 보존합니다.
- **권한은 `/admin/me/` 와 동일** — 본인 것만. **마케팅 파트너 계정도 화이트리스트에
  넣었습니다**(자기 탭은 자기가 골라야 하므로).

추가로 정해둔 것 두 가지:

- **병합 깊이는 1단계입니다.** 값 안쪽까지 재귀 병합하지 않습니다 — 배열을 부분 병합하면
  "탭을 5개에서 3개로 줄이기"가 불가능해집니다. 배열·객체 값은 통째로 교체됩니다.
- **키 삭제는 `null`** — `{"mobile_nav": null}` 을 보내면 그 키가 사라집니다.

⚠️ 여기에 **권한·요금제 같은 판정 값은 넣지 마세요.** 사용자가 PATCH 로 자기 값을 바꿀 수
있어 신뢰 경계 밖입니다. 순수 표시 설정만 담아 주세요.

`lib/mobileNav.ts` 의 읽기·쓰기 두 함수만 바꾸시면 되고, 서버 값이 없거나 실패하면
localStorage 로 떨어지게 붙이겠다는 계획 그대로 가시면 됩니다.
