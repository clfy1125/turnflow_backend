## MKT-16. 답: 첫 번째 줄입니다 — 스니펫이 7/22 부터

요청하신 두 쿼리 결과입니다 (prod, 2026-08-19 조회).

```
MIN(created_at)             2026-07-22 09:14:34 KST
MAX(created_at)             2026-08-19 14:31:28 KST
COUNT(*)                    777
COUNT(DISTINCT visitor_id)  509
```

| 월 | 세션 | 방문자 |
|---|---|---|
| 2026-07 | 229 | 179 |
| 2026-08 | 548 | 371 |

**7월 이전 행은 아예 없습니다.** 30일·90일·전체 기간 창이 전부 `(777세션, 509명)` 으로
나와 화면에서 보신 509와 일치합니다. 추정하신 대로 30일 탭이 이미 원본 전체를 덮고 있어서
세 기간이 같은 값이 된 것이고, `_visit_counts` 는 정상 동작하고 있었습니다.

### 두 번째 줄(보존 배치가 지우고 있다)은 배제됐습니다 — 근거 3개

1. `LANDING_VISIT_RETENTION_DAYS` = **180** (운영 컨테이너 실측). `.env.production` 에 키
   자체가 없어 코드 기본값 180이 그대로 쓰이고 있습니다. 30 근처가 아닙니다.
2. 그 값이면 cutoff 는 `now - 180d` = **2026-02-20** 이라 삭제 대상이 0건입니다.
3. **pk 가 1부터 777까지 결번 없이 연속**이고 `COUNT(*)` 도 777입니다.
   → `analytics.cleanup_landing_visits` 의 `deleted` 누적치는 **0** 이고, 이 테이블에서
   지워진 행은 지금까지 한 건도 없습니다.

`MIN` 이 마침 28일 전이라 30일 보존과 헷갈릴 수 있는 모양이었는데, pk 연속성으로 갈렸습니다.
**90일·전체 기간 지표가 앞으로 계속 30일치로 남는 문제는 없습니다** — 원본은 날이 갈수록
쌓이기만 하고, 실제로 세 기간의 값은 8월 22일(=7/22 + 30일)부터 자연히 갈라지기 시작합니다.

### 덤 — `since` 를 대용할 수 없다는 지적도 맞았습니다

```
attribution_gap.since (SignupAttribution 최초)  2026-07-16 07:29 KST   (113행)
visits_since          (LandingVisit 최초)       2026-07-22 09:14 KST
```

**6일 차이**입니다. 가입 귀속과 방문 비콘의 배포 시점이 달랐습니다.

## MKT-17 ①. `visits_since` 추가 (배포됨)

제안하신 자리 그대로 `channels.attribution_gap` 안에 넣었습니다.

```jsonc
"channels": {
  "attribution_gap": {
    "signups_unattributed": 1,
    "share": 0.0103,
    "since":        "2026-07-16T07:29:01.586329+09:00",  // 가입 귀속 계측 시작
    "visits_since": "2026-07-22T09:14:34.030914+09:00"   // ← 신규: 방문 계측 시작
  }
}
```

- 전 기간 `MIN(LandingVisit.created_at)` 입니다. **기간 파라미터와 무관**하게 같은 값이 옵니다.
- 어트리뷰션 미탑재(`attribution_available=false`)면 `null` 입니다.
- `created_at` 이 인덱스 컬럼이라 쿼리 1회 추가에 그칩니다(응답 캐시도 그대로).

## MKT-17 ②. null 처리 — 보류 중입니다

**요청하신 순서를 지킵니다: 프론트 배포 → 서버 변경.** 지금은 넣지 않았습니다.

프론트에서 퍼널 노드 `count` 스키마를 nullable 로 바꿔 배포하신 뒤 알려주시면, 그때
`선택 기간 시작 < visits_since` 인 경우 `funnel.variants[*].head[0].count` 와 signup 노드의
`rate` 를 null 로 내리는 변경을 별도 배포하겠습니다. 판단 근거(②가 낫다)에 동의합니다 —
분모를 잘라 다시 계산하면 분자도 잘라야 하고, 그건 사실상 `visits_since` 부터의 새 기간입니다.

그때까지 전체 기간 32.2% / 90일 26.1% 는 **과대평가된 채로 나갑니다.** 외주 파트너에게
전달되는 화면이라면, 그 사이에는 30일 탭만 쓰시는 편이 안전합니다(30일은 분자·분모가 같은
기간을 셉니다).

## MKT-18. 방문 숫자를 사람 단위로 통일 (①②  둘 다 배포됨)

지적하신 대로 한 화면이 방문을 세 정의로 세고 있었습니다. `trends` 만 세션이었습니다.

### ① `visits` 를 고유 방문자 수로

`trends.buckets[].visits` 와 `trends.buckets[].by_channel[].visits` **둘 다** 바꿨습니다.
이제 화면의 방문 관련 숫자가 전부 사람 단위이고, 채널별 성과 표의 `visits` 와 정의가 같습니다.

세션 수가 필요하면 **`kpis.visits`** 가 그대로 세션을 들고 있습니다(변경 없음).

### ② `trends.totals` 추가

```jsonc
"trends": {
  "granularity": "day",
  "buckets": [ /* ... */ ],
  "totals": { "visits": 510, "signups": 97, "activated": 71, "paid": 5 }  // ← 신규
}
```

`totals.visits` 는 퍼널 `방문자`(`funnel.variants.*.head[0].count`)와 **항상 같은 값**입니다.
배포 후 prod 30일 실측:

| | 값 |
|---|---|
| 버킷 합 (지금 헤더가 만드는 값) | **695** |
| `totals.visits` = 퍼널 방문자 | **510** |

말씀하신 대로 버킷을 더하면 실제 인원보다 커집니다(재방문자가 두 버킷에 각각 들어갑니다).
헤더를 `trends.totals` 로 갈아타시면 화면 두 곳이 처음으로 일치합니다.

### ⚠️ 함께 바뀐 계약 하나 — `by_channel` 합은 이제 **부등식**입니다

```
이전:  Σby_channel.visits  ==  버킷 visits
이후:  Σby_channel.visits  >=  버킷 visits
```

같은 방문자가 한 버킷 안에서 두 채널로 들어오면 양쪽 집합에 각각 1로 잡히기 때문입니다
(각 값은 그 자체로 정확한 고유 방문자 수입니다). 채널별 성과 표의
`Σsources.visits >= other.visits` 와 같은 성질입니다.

prod 실측(30일, 29버킷)에서 **2버킷**이 여기 해당합니다: 08-06(29 vs 28), 07-30(20 vs 19).
스택 막대의 층 합계로 버킷 총량을 검산하는 로직이 있다면 등호 단언을 풀어 주세요.

사람 단위 3지표(`signups`/`activated`/`paid`)의 항등은 **그대로**입니다:
`Σby_channel[m] + unattributed[m] == 버킷[m]`.

### `totals.activated` 만 퍼널과 정의가 다릅니다

- 퍼널 `activation` 노드 = **이 기간에 가입한** 회원이 현재까지 활성화했는가 (가입 코호트)
- `trends.totals.activated` = 가입 시기와 무관한 **이 기간의 활성화 이벤트** (버킷 단위 dedupe를
  기간 전체로 확장)

추이 카드 헤더용이라 버킷과 같은 정의를 씁니다. 퍼널 숫자와 다른 것이 정상입니다.
