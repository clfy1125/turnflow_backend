## 1. dev — `celery_beat` 가 죽어 있었습니다

```
instagram_backend_celery_beat  | ERROR: Pidfile (/tmp/celerybeat.pid) already exists.
instagram_backend_celery_beat  | Seems we're already running? (pid: 1)
```

compose 가 `--pidfile=/tmp/celerybeat.pid` 로 beat 를 띄우는데, 컨테이너가 재시작되면
**죽은 프로세스의 pid 파일이 그대로 남아** beat 가 "이미 실행 중"으로 오판합니다.
`restart: unless-stopped` 와 맞물려 **영구 크래시 루프**가 됐고, 그 동안 dev 의
**주기잡이 전부 멈춰** 있었습니다(체험 만료만이 아닙니다).

`--pidfile` 을 제거했습니다 — 컨테이너 1개 = 프로세스 1개라 그 가드는 가치가 없고
이 실패 모드만 만듭니다.

**복구 확인**

| | 전 | 후 |
|---|---|---|
| `baby422p@naver.com` (사장님 dev) | `pro` / `trialing` | **`free` / `active`** |
| 기간 지났는데 `trialing` 인 무카드 계정 | 3건 | **0건** |

> 재시드한 테스트 계정들도 영향을 받았던 것이라, dev 에서 **다른 주기 기능도 며칠째
> 멈춰 있었습니다**(댓글 누락 보정, 썸네일 스위퍼 등). 지금은 전부 돕니다.

보고 발사하는 구조입니다. 그래서 dev 의 beat 고장과 **경로가 다릅니다.**

## 3. 배치 시각 — ⚠️ 문구와 기준이 다릅니다 (결정 필요)

**매시 22분, 1시간 주기**입니다. 다만 기준점이 말씀하신 것과 다릅니다.

> 「마지막 이용일 다음 날 0시(KST) 무렵에 무료가 되는 것이 문구와 맞습니다」

맞는 지적입니다만, **지금 서버는 그렇게 동작하지 않습니다.**

### 왜 어긋나나

체험 종료 시각은 **지급 시각 + 30일**이라 날짜 경계가 아니라 **임의의 시:분**입니다.

```
지급   2026-09-14 14:06 KST
       ↓ +30일
종료   2026-10-14 14:06 KST   ← trial_ends_at (current_period_end)
       ↓ localdate - 1일
표기   2026-10-13             ← trial_last_day (화면 문구)
```

그래서 실제 동작은 이렇습니다.

| 시각 (KST) | 서버 | 화면(현재 프론트) |
|---|---|---|
| 10-13 23:59 | 프로 / `trialing` | 프로 체험 |
| **10-14 00:00** | **프로 / `trialing`** (그대로) | **무료** ← 여기서 갈림 |
| 10-14 14:06 | 기간 종료(아직 `trialing`) | 무료 |
| **10-14 14:22** | **무료 / `active`** (배치) | 무료 |

**즉 화면이 「무료」라고 말한 뒤에도 서버는 최대 ~24시간 더 프로를 줍니다.**
(사용자에게 불리한 방향은 아닙니다 — 더 주는 쪽입니다.)

### 선택지

| | 내용 | 영향 |
|---|---|---|
| **A. 그대로** | 종료는 `trial_ends_at` 시각 기준 | 지금 상태. 프론트 보정으로 화면만 맞춤 |
| **B. 문구에 맞춤** | 마지막 이용일 다음 날 **0시**에 내린다 | 이미 준 프로를 **최대 24시간 앞당겨 회수**. 고지한 것보다 덜 주게 되진 않지만, 쓰던 기능이 예정보다 일찍 끊김 |
| **C. 문구를 사실에 맞춤** | `trial_last_day` 를 `종료일 당일`로(= 10-14) | 아무것도 회수하지 않음. 다만 **고지 문구가 바뀌므로** 결제 전 고지·동의 문안과 같이 봐야 함 |

**백엔드 의견은 C 입니다** — 사용자에게서 아무것도 빼앗지 않고 문구만 사실과 맞춥니다.
다만 `trial_last_day` 는 결제 전 고지(`PaymentConsent`)에 그대로 들어가는 값이라
**사장님·법무 확인이 필요한 제품 결정**이라 제가 임의로 바꾸지 않았습니다.

그때까지는 **지금 하신 클라이언트 보정이 합리적입니다.** 다만 그 구간에서 화면은
「무료」인데 **프로 기능·한도는 아직 살아 있다**는 점만 알고 계시면 됩니다
(말씀하신 대로 권한·한도는 배치가 바꾸는 게 맞습니다).

## 4. 기간이 지났는데 `trialing` 일 때 카드 등록 — **결함이었고 고쳤습니다**

### 종전 동작 (잘못)

`status == trialing` 이기만 하면 **기간이 이미 지났어도** `attach_only` 로 갔습니다.

```jsonc
// 체험이 10분 전에 끝난 계정이 카드 등록
{ "scenario": "attach_only",
  "first_charge_at": "2026-10-13 14:00",   // ← 과거!
  "detail": "카드가 등록되었습니다. 체험 종료 시 첫 결제가 진행됩니다." }
```

그리고 `process_due_renewals`(10분 주기)가 **즉시** 긁습니다.
사용자는 "체험 종료 시 결제"를 읽고 **10분 안에 결제**됩니다. 그 과거 시각이 그대로
결제 전 고지 기록(`PaymentConsent.disclosed_first_charge_at`)에 박히므로 **허위 고지**입니다.

프론트가 `trial_last_day` 가 지나면 곧바로 「체험이 끝났어요 / 카드 등록」을 띄우므로
이 창은 **실제로 밟힙니다.**

### 고친 뒤

기간이 끝난 **무카드** 체험은 **`charge_now`** 로 갑니다 — 배치가 돈 뒤와 같은 결론입니다.

| 상태 | `scenario` | `first_charge_at` |
|---|---|---|
| 체험 남음 (+3일) | `attach_only` | 3일 뒤 (미래) ✅ |
| **체험 끝남 (-10분)** | **`charge_now`** | **지금** ✅ |
| 체험 끝남 (-2일) | `charge_now` | 지금 ✅ |

부수 효과로 좋아진 것 둘:

- **플랜 변경 가능** — 체험이 끝났으므로 프로 대신 베이직을 골라 결제할 수 있습니다
  (체험 중에는 계속 금지입니다).
- **레이스 무해** — 배치가 먼저 돌든 사용자가 먼저 누르든 **결과가 같습니다.**

> ⚠️ **카드가 이미 있는 체험은 바꾸지 않았습니다.** 그쪽 첫 과금은 갱신 파이프라인이
> 소유하고 멱등 키로 중복을 막습니다. 여기서 `charge_now` 로 바꾸면 **이중 과금**이 납니다.
> 그 경우 `first_charge_at` 이 잠깐(≤10분) 과거로 보일 수 있는데, 실제로 그 직후 결제되므로
> 의미상 틀리지 않습니다.

**프론트 작업은 없습니다** — 같은 엔드포인트가 상황에 맞는 `scenario` 를 돌려줍니다.
다만 「체험 종료 시 결제」 문구는 `scenario === "attach_only"` 일 때만 쓰시고,
`charge_now` 면 **「지금 결제됩니다」**로 보여 주시면 화면이 서버와 완전히 맞습니다.
